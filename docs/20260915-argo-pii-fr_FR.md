# PII 목록: fr_FR (프랑스)

이 문서는 `tinicore/src/guardrails/config/pii_filter_config.yaml` 에 프랑스(fr_FR) 고유 PII recognizer 가 포함되어야 하는 근거를 기록한다. 이미 YAML 에 있는 항목도 근거를 남기기 위해 포함하며, 국가에 종속되지 않는 항목(카드번호, API 키, 비밀번호, 이메일, IP 주소 등)은 다루지 않는다. 2026-09-15 현재 YAML 에 `fr_*` recognizer 는 하나도 없으므로 이 문서의 모든 항목은 신규이다.

## 0. 문서 작성 기준

각 항목은 다음 네 가지 기준으로 평가한다.

1. 적용 법령 또는 감독기관 규제상 노출되면 안 되는 PII 인가?
2. 그 PII 가 무엇이며, 노출을 막아야 하는 근거는 무엇인가?
3. 결정론적 방법(regex 또는 손으로 작성한 패턴 매칭)으로 검출할 수 있는가?
4. 검증기(체크섬 등)가 있어서 매칭 정확도를 높일 수 있는가? 검증기가 없어도 보안상 중요하면 채택한다.

### 검출 방식 세 가지 (결정론적 검출 가능성 항목에서 사용하는 용어)

엔진(`recognizer.rs` 의 `PiiEngine`)은 세 가지 매칭 방식을 지원하며, 어느 방식으로 찾은 매치든 같은 후처리 파이프라인(boundary check → validator → dedup → 점수 계산·임계값)을 거친다. 따라서 검증기와 context_words 는 방식과 무관하게 동일하게 적용된다.

| 방식 | 구현 위치 | 동작 | 적합한 경우 | 비용 |
|---|---|---|---|---|
| **regex** | `PatternRecognizer`, `PatternTemplateRecognizer` | 패턴을 30개 단위 청크(`DEFAULT_CHUNK_SIZE`)로 나눠 `regex_automata::hybrid::dfa`(lazy DFA)로 컴파일하고, 청크마다 텍스트를 한 번씩 스캔 | 패턴 수가 적고 구조가 단순할 때. 기본 선택지 | 패턴 수와 복잡도에 비례해 DFA 캐시 메모리와 스캔 횟수가 늘어난다. 카드번호는 105개 패턴이 문제가 되어 handwritten 으로 옮겼다 |
| **byte-scan handwritten** | `handwritten/card_detector.rs` 방식 (`MatchEngine` 직접 구현) | 텍스트를 바이트 단위로 걸으며 숫자열·영숫자열을 뽑고, 접두 표·길이·자리 규칙을 코드로 검사 | 접두가 고정 문자열이 아니라 **표**(BIN 처럼 여러 접두 구간)이거나, 주별 형식처럼 패턴 수가 많거나, 체크섬을 매칭 단계에서 바로 적용하고 싶을 때 | 메모리 거의 없음. 타입마다 detector 코드를 작성해야 한다 |
| **Aho-Corasick handwritten** | `handwritten/aho_corasick_detector.rs` (`pattern_desc_for` 에 anchor + verifier 등록) | 고정 문자열 anchor 를 하나의 automaton 으로 찾고, anchor 뒤의 바이트를 verifier 함수가 검사 | **고정 리터럴 접두**가 있고 그 뒤에 단순한 문자 집합 run 이 이어질 때 (`AKIA`, `ghp_`, `010` 등). 여러 타입을 한 automaton 에 묶어 텍스트를 한 번만 스캔한다 | 메모리 거의 없음. anchor 가 짧으면(1-2바이트) 텍스트 곳곳에서 verifier 가 호출되어 이득이 줄고, anchor 는 대소문자를 구분한다(`ascii_case_insensitive` 미사용) |

각 항목의 "결정론적 검출 가능성"에서는 regex 를 기본으로 표로 기술하고, 그 아래에 handwritten(byte-scan, Aho-Corasick) 대안의 실현 가능성과 **오탐률이 regex 대비 어떻게 달라지는지**를 함께 적는다. 오탐률은 매칭 형식이 같으면 방식과 무관하게 같고, handwritten 이 매칭 단계에서 표 대조나 체크섬을 추가로 수행하거나 (카드번호처럼) 구분자 제약을 의도적으로 풀 때만 달라진다.

### 점수 체계와 context_words (정확도가 낮은 패턴에 반드시 적용)

**현재 코드에서 context_words 는 매치를 걸러내지 않는다.** `compute_score` (`recognizer.rs`)는 context 단어가 매치 주변 ±50자 안에 있으면 1.0, 없으면 0.5 를 돌려주고, 임계값 `SCORE_THRESHOLD` 도 0.5 이므로 context 단어가 없어도 모든 매치가 살아남는다. 점수는 겹침 해소(`detector.rs`)에서 어느 매치를 우선할지 정하는 데에만 쓰인다. 따라서 "context_words 가 있으니 오탐을 걸러준다"는 가정은 현재 성립하지 않는다.

이 문서의 regex 표에서 **"score 사용 필요"** 로 표시한 패턴은, 형식만으로는 정확도가 낮아서 context 단어 없이 매칭되면 오탐이 될 가능성이 높은 것들이다. 이런 패턴을 채택하려면 Presidio 와 같은 방식의 점수 체계가 먼저 있어야 한다.

- `RecognizerConfig` 와 `PatternMeta` 에 recognizer 단위 `score` 필드(기본값 0.5)를 추가한다.
- `compute_score` 를 "기본 점수 + context 가산" 방식으로 바꾸고 임계값 0.5 는 유지한다. 가산값은 **0.5** 를 권장한다. 그러면 기존 recognizer 의 context 매치 점수가 지금과 같은 1.0 으로 유지되어 `tinicore/tests/guardrails/filter_test.rs` 의 `score == 1.0` 단정 3건(5331, 5441, 5471행)이 그대로 통과한다. Presidio 기본값 0.35 를 쓰면 통과·탈락 결과는 같지만 점수가 0.85 로 바뀌어 이 테스트들을 갱신해야 한다.
- 기존 recognizer 는 모두 기본값 0.5 이므로 통과·탈락 결과가 바뀌지 않는다. `card_number` 와 Aho-Corasick 계열은 Luhn 과 고정 접두가 이미 강한 필터라서 `score` 를 지정할 필요가 없다. `PatternMeta` 를 통해 같은 파이프라인을 타지만 값이 기본이라 영향이 없다.
- 낮은 `score` 를 준 recognizer 에는 `context_words` 를 반드시 채워야 한다. `compute_score` 는 `context_words` 가 비어 있으면 가산 없이 기본 점수를 돌려주므로, 비워 두면 모든 매치가 탈락한다.
- 정확도가 낮은 패턴은 같은 `pii_type` 을 가진 별도 recognizer(예: `us_driver_license_numeric`)로 분리해 `score: 0.3` 처럼 낮게 준다. context 없이는 0.3 으로 탈락하고, context 가 있으면 0.8 로 통과한다. pid 가 패턴 단위이고 `PatternMeta` 가 recognizer 설정을 패턴마다 복제하므로, 패턴별 점수보다 recognizer 분리가 스키마 변경이 적다.

context_words 는 소문자 부분 문자열 검색이므로 `car`, `tin`, `ead`, `ach`, `aba` 같은 짧은 단어는 `card`, `routing`, `read` 안에서도 걸린다. 점수 체계를 도입하면 이런 단어가 가산의 근거가 되므로, 짧은 단어는 목록에서 빼거나 앞뒤에 공백을 포함한 형태로 등록해야 한다.

### 엔진 제약 (regex 작성 시 유의)

- lazy DFA 이므로 **lookahead·lookbehind·역참조를 쓸 수 없다.** 배제 규칙(예: 특정 접두·구간을 발급하지 않는 번호에서 그 값을 제외하는 규칙. en_US 의 SSN `000`·`666`·`9xx` 배제가 대표 사례)은 regex 가 아니라 `validator.rs` 의 검증 함수로 구현하거나, handwritten detector 안에서 코드로 처리한다.
- 현재 `validator.rs` 에 존재하는 검증기는 `luhn`, `rrn`, `phonenumber` 세 가지뿐이다. `rrn` 은 자릿수만 확인하고 `phonenumber` 는 항상 `true` 를 돌려준다. 아래 "검증기" 필드에서 "현재"는 이 세 가지 기준이고, "구현 가능"은 새로 작성해야 하는 검증 논리를 뜻한다.
- **`validator::validate` 는 fail-open 이다.** 모르는 검증기 이름이 오면 `true` 를 돌려준다. 따라서 YAML 에 `ssn`, `aba_routing` 같은 이름을 먼저 적고 함수를 나중에 구현하면 경고 없이 모든 매치가 통과한다. 반드시 **검증기 구현 → YAML 등록** 순서로 작업한다.
- 단어 경계 처리는 `boundary_check` 와 `boundary_check_reject_before/after` 설정으로 한다. `config.rs` 의 `boundary_check_reject_before` 필드 주석은 패턴 안의 `(?-u:\b)` 대신 이 설정을 쓰도록 안내한다(DFA 상태 수 감소). handwritten detector 도 같은 설정을 따른다.
- `RecognizerConfig` 에 대소문자 무시 옵션이 없다. 소문자 입력까지 잡으려면 패턴 안에 `(?i)` 인라인 플래그를 넣거나 문자 클래스에 소문자를 포함해야 한다. 기존 `us_passport` 는 `[a-zA-Z]` 로 소문자를 허용하고, 각 국가 문서의 신규 제안은 대문자 `[A-Z]` 만 쓰는 것을 기본으로 한다. 구현 시 통일한다.

### regex 표의 형식

각 항목의 regex 는 다음 3열 표로 기술한다. 표에 실린 모든 regex 는 Python `re` 로 예시와의 매칭을 확인했다(`(?-u:\b)` 는 `\b` 로 치환, `boundary_check` 는 인접 문자 검사로 모사).

| regex | 매칭 예시 | 비고 (score 사용 필요 등) |
|---|---|---|

"비고" 열의 표기는 다음 뜻이다.
- **score 사용 필요**: 형식만으로는 정확도가 낮다. 점수 체계 도입 후 낮은 `score` 로 등록해서 context 단어가 있을 때만 통과시킨다. 신규 패턴은 점수 체계가 없는 동안 등록하지 않는다. 이미 YAML 에 있는 기존 recognizer(en_US 의 `us_passport` 등)는 예외로, 현재 상태(오탐 감수)로 유지하다가 점수 체계 도입 후 낮은 `score` 로 전환한다.
- **score 사용 고려**: 형식만으로는 정확도가 중간이다. 검증기가 있으면 기본 점수로 충분하고, 검증기가 없거나 검증기 없이 등록한다면 낮은 `score` 를 권장한다.
- **기본**: 형식 자체가 충분히 특이해서 기본 점수 0.5 로 등록해도 된다.


### 이 문서의 regex 검증 방법에 대한 보충

엔진은 DFA 를 `MatchKind::All` 로 빌드해 겹치는 모든 매치 끝을 보고한 뒤 boundary check 와 dedup 으로 가장 긴 것을 남긴다. 또한 엔진이 `unicode(false)` 로 DFA 를 빌드하므로 악상 문자(`é`, `è` 등)는 문자 클래스에 넣을 수 없고 리터럴 대안으로만 쓸 수 있다(ko_KR·de_DE 문서와 같은 이유). 이 문서의 regex 는 모두 ASCII 만 쓰므로 해당 사항이 없고, context_words 의 악상 문자는 소문자 부분 문자열 검색이라 문제가 없다.

## 1. 적용 법령 및 감독기관

프랑스는 EU 회원국이므로 GDPR 이 직접 적용되고, 1978년 정보처리와 자유에 관한 법률(Loi Informatique et Libertés, 이하 LIL)이 GDPR 의 개방 조항을 채우는 국내 이행법이다. 감독기관은 CNIL 단일 기관이다. 프랑스 법제의 특징은 **NIR(사회보장번호)의 처리를 LIL 제30조가 국사원 데크레(décret en Conseil d'État)로 제한**한다는 점으로, GDPR 제87조가 위임한 국가 식별번호 규율의 대표 사례이다. 2019년 데크레(n° 2019-341)가 NIR 처리가 허용되는 목적을 한정 열거한다. 이 문서는 NIR 을 최우선 채택 대상으로 하고, 나머지는 CNIL 이 개인정보로 다루는 식별자 순으로 평가한다.

| 법령 | 감독기관 | 적용 범위 요약 |
|---|---|---|
| GDPR (Regulation (EU) 2016/679) 제4조, 제9조, 제32조, 제87조 | CNIL (Commission nationale de l'informatique et des libertés) | 개인정보 정의, 특수 범주, 처리 보안, 국가 식별번호 이용 조건 위임 |

| Code de la sécurité sociale (CSS) 제L.114-12-1조 | CNAV, INSEE, 사회보장 기관 | NIR 을 키로 하는 사회보장 수급자 공통 저장소(RNCPS) |

| fr_phonenumber | 전화번호 (0X XX XX XX XX) | 가능 | regex | 없음 / 없음 (접두 규칙은 regex 에 포함) | 사용 고려 | 신규 | 채택 |
| fr_vehicle_plate | 차량 번호판 (SIV `AA-123-AA`, 구형 FNI) | 가능 | regex | 없음 / 없음 | 기본 (SIV) / **사용 필요** (FNI) | 신규 | 채택 (SIV 는 바로, FNI 는 점수 체계 도입이 선행 조건) |
| fr_siren_siret | 사업자 번호 (SIREN 9자리, SIRET 14자리) | 가능 | regex (+ `luhn` 검증기) | `luhn` (기존) / 그대로 사용 가능 | 사용 고려 | 신규 | 미채택 (보류) |

이외에 검토했으나 결정론적 검출이 불가능하거나 공개 번호라서 미채택한 항목은 4절에 정리했다.

## 3. 항목별 상세

### fr_nir

- **설명**: NIR (numéro d'inscription au répertoire), 통칭 사회보장번호(numéro de sécurité sociale). INSEE 가 출생 시 부여하는 13자리 번호 + 2자리 키 = 15자리이며, 구조는 `S YY MM DD CCC OOO KK` 이다. `S` 는 성별(`1` 남, `2` 여), `YY` 출생 연도, `MM` 출생 월(`01`-`12`. 월 미상은 `20`, 해외 출생 등 특수 등록은 `30`-`42`·`50`-`99`), `DD` 출생 데파르트망(`01`-`95`, 코르시카는 `2A`·`2B`, 해외 데파르트망 `97`·`98`, 외국 출생 `99`), `CCC` 코뮌 또는 국가 코드, `OOO` 출생 등록 순번, `KK` 는 mod 97 키이다. Carte Vitale(건강보험 카드)에 인쇄되며, 국가 건강 식별자(INS)로도 쓰인다. 서면에서는 `2 69 05 49 588 157 80` 처럼 띄어 쓴다.
  - 예시: `2 69 05 49 588 157 80` (프랑스어 위키백과가 구조 설명에 쓰는 예시. 키 `80` 을 통과한다), `1 85 05 78 006 084 91` (계산으로 만든 형식 예시), `1 94 01 2A 004 015 47` (코르시카 치환 규칙을 적용한 형식 예시)
- **법적 근거**:
  - 법령: LIL 제30조 (NIR 처리는 국사원 데크레로만 허용), Décret n° 2019-341 (허용 목적 한정), CSS 제L.114-12-1조, CSP 제L.1111-8-1조 (INS), GDPR 제87조
  - 감독기관: CNIL, INSEE, CNAV
  - 노출 금지 이유: 프랑스에서 법률이 처리 자체를 원칙적으로 금지하는 유일한 번호이다. 성별·출생 연월·출생지가 번호 안에 그대로 들어 있어 번호 자체가 개인정보를 드러내고, 건강보험·연금·고용·조세 기록의 연결 키이다. CNIL 은 NIR 을 목적 외로 저장한 기업에 반복적으로 제재를 부과해 왔다.
- **결정론적 검출 가능성**: 가능하며 형식이 엄격하다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[12] ?[0-9]{2} ?(0[1-9]\|1[0-2]\|20\|3[0-9]\|4[0-2]\|[5-9][0-9]) ?([0-9]{2}\|2[AB]) ?[0-9]{3} ?[0-9]{3} ?[0-9]{2}` | `2 69 05 49 588 157 80`, `269054958815780`, `2690549588157 80`, `1 94 01 2A 004 015 47`, `1850578006084 91` (`3 69 05 …`(성별 3), `2 69 13 …`(월 13), 키 없는 13자리는 거부) | 기본. 첫 자리 `1`/`2`, 월 구간, 15자리 고정 길이에 `fr_nir` 검증기(mod 97, 우연히 통과할 확률 1/97)를 더하면 오탐이 매우 낮다. 데파르트망 `([0-9]{2}\|2[AB])` 는 존재하지 않는 `00`·`96` 도 허용하므로 검증기에서 배제한다. `boundary_check: true` 적용 |

    오탐: 낮다. 구분자 없는 15자리 숫자열은 다른 번호와 겹칠 수 있으나 검증기가 거의 모두 걸러낸다. 성별 코드 `3`·`4` 는 과거 임시 등록용이라 제외했다. `7`·`8` 로 시작하는 NIA(numéro identifiant d'attente, NIR 대기자용 임시 번호)는 현재도 부여된다는 자료가 있으므로(확인 필요), 포함하려면 첫 자리를 `[1278]` 로 넓힌다.
  - **byte-scan handwritten**: 가능. 숫자열(코르시카 `2A`/`2B` 포함)을 뽑아 mod 97 키를 매칭 단계에서 계산한다. 오탐률은 regex + `fr_nir` 조합과 **동일**하다.
  - **Aho-Corasick**: 부적합. 접두가 `1`/`2` 한 글자라 anchor 로 쓸 수 없다.
  - **권장**: regex + `fr_nir` 검증기.
- **검증기**:
  - 현재: 없음
  - 구현 가능: mod 97 키. 앞 13자리를 정수로 읽어 `97 - (n mod 97)` 이 마지막 2자리와 같으면 유효하다. 코르시카는 데파르트망 자리의 `2A` 를 `19` 로, `2B` 를 `18` 로 **치환만** 하고 계산한다(문자를 `0` 으로 바꿔 `20` 을 만든 뒤 1,000,000 또는 2,000,000 을 빼는 표기법도 같은 결과이며, 두 방식을 겹쳐 적용하면 안 된다. python-stdnum `fr/nir.py` 와 대조해 확인). 데파르트망 `00`·`96` 은 존재하지 않으므로 검증기에서 함께 배제할 수 있다. 검증기 `fr_nir` 로 구현한다.
- **채택 여부 및 근거**: 채택. 법률이 처리를 제한하는 최고 등급 식별자이며 강한 검증기가 있다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `sécurité sociale`, `securite sociale`, `carte vitale`, `vitale`, `assuré`, `ameli`, `cpam`, `insee`, `social security`. (`nir` 은 `finir`·`venir` 에, `sécu` 는 `sécurité` 에 포함되므로 ` nir ` 처럼 공백 포함 형태로 쓰거나 제외한다.)

### fr_tax_number

- **설명**: numéro fiscal (numéro d'identification fiscale, SPI). DGFiP 가 개인 납세자에게 부여하는 13자리 번호이며 첫 자리는 `0`-`3` 이다. 소득세 신고서와 세금 고지서에 인쇄되고 온라인 세무 계정(impots.gouv.fr) 로그인 ID 로 쓰인다. 마지막 3자리는 앞 10자리를 511 로 나눈 나머지인 체크섬이다(EU 집행위 TIN 국가 시트, python-stdnum `fr/nif.py` 기준).
  - 예시: `0123456789211`, `3012345678167` (형식 예시. mod 511 체크섬을 통과하도록 계산한 값), `3023217600053` (python-stdnum 문서의 예시)
- **법적 근거**:
  - 법령: LPF 제L.103조 (조세 비밀), CGI, GDPR 제87조
  - 감독기관: DGFiP, CNIL
  - 노출 금지 이유: 세무 계정 접근과 세금 환급 사기의 열쇠이다. 2019년 이후 원천징수 도입으로 고용주도 이 번호를 다루므로 유출 경로가 넓어졌다.
- **결정론적 검출 가능성**: 가능하나 정밀도가 낮다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-3][0-9]{12}` | `0123456789211`, `3012345678167`, `3023217600053` (`4123456789012`, 12자리는 거부) | score 사용 고려. 첫 자리 제한 외에는 13자리 숫자열이라 주문번호·바코드(EAN-13 도 13자리)와 겹치므로 `fr_spi` 검증기(mod 511, 우연히 통과할 확률 1/511) 병행이 사실상 필수이다. 검증기 없이 등록한다면 score 사용 필요 |

    오탐: 검증기 없이는 높다. EAN-13 바코드는 프랑스 제품에서 `3` 으로 시작하는 경우가 많아 특히 충돌하지만, mod 511 검증기가 511개 중 1개만 통과시키므로 대부분 해소된다. `boundary_check: true` 적용.
  - **byte-scan handwritten**: 가능. 오탐률은 regex + `fr_spi` 조합과 **동일**하다.
  - **Aho-Corasick**: 부적합.
  - **권장**: regex + `fr_spi` 검증기.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 앞 10자리를 정수로 읽어 511 로 나눈 나머지를 3자리로 맞춘 값이 마지막 3자리와 같으면 유효하다. 검증기 `fr_spi` 로 구현한다.
- **채택 여부 및 근거**: 채택. 조세 비밀 대상이고 세무 계정의 열쇠이며, `fr_spi` 검증기로 오탐을 제어할 수 있다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `numéro fiscal`, `numero fiscal`, `identifiant fiscal`, `impôts`, `impots`, `dgfip`, `avis d'imposition`, `déclaration de revenus`, `tax number`. (`spi` 는 3글자라 제외한다.)

### fr_passport

- **설명**: 여권번호. 2006년 이후 전자여권은 숫자 2자리 + 영문 대문자 2자리 + 숫자 5자리의 9자리이다(예: `12AB34567`). 앞 2자리는 발급 연도 뒷자리로 알려져 있다(확인 필요). 번호 자체에는 체크섬이 없고 MRZ 에 7-3-1 체크 디지트가 붙는다.
  - 예시: `12AB34567`, `19FV12345` (형식 예시)
- **법적 근거**:
  - 법령: GDPR 제4조·제87조, LIL, Décret n° 2005-1726 (전자여권), Code pénal 제226-16조 이하
  - 감독기관: CNIL, 내무부 (ANTS)
  - 노출 금지 이유: 정부 발급 신분증 번호로서 항공·호텔·은행 KYC 에 쓰이고 신원 도용에 직결된다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{2}[A-Z]{2}[0-9]{5}[0-9]?` | `12AB34567`, `19FV12345` (`1AB34567`, 소문자 `12ab34567` 은 거부) | score 사용 고려. `숫자 2 + 대문자 2 + 숫자 5` 는 비교적 특이하지만 제품 코드·예약 번호와 겹칠 수 있다. 선택 꼬리 `[0-9]?` 는 MRZ 체크 디지트가 함께 적힌 10자리 표기를 잡기 위한 것이며 de_DE 와 같이 10자리 매치에만 `mrz_731` 검증기를 적용한다. `boundary_check: true` 적용 |

    오탐: 중간.
  - **byte-scan handwritten**: 가능하나 이득이 없다.
  - **Aho-Corasick**: 부적합. 고정 접두가 없다.
  - **권장**: regex + `mrz_731` 검증기(10자리 매치에만). 9자리 단독 표기에는 검증기를 적용할 수 없다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 번호 자체에는 없다. MRZ 체크 디지트가 동반된 10자리 표기는 de_DE 문서의 `mrz_731`(ICAO 9303, 7-3-1 가중)로 검증한다.
- **비고**: `fr_id_card` 의 신형 패턴 `[0-9A-Z]{9}` 는 이 패턴의 상위집합이라 같은 값이 두 recognizer 에 동시에 매치된다. 운전면허 카드형 번호가 여권과 같은 형식으로 확인되면 세 recognizer 가 같은 값을 잡게 되므로, 그 경우 하나의 `pii_type`(예: `fr_id_document`)으로 통합하거나 context_words 로 우선순위를 정하는 방안을 구현 시 결정한다.
- **채택 여부 및 근거**: 채택. 정부 발급 신분증 번호이며 형식이 비교적 특이하다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `passeport`, `passport`, `numéro de passeport`, `n° passeport`, `titre de voyage`

### fr_id_card

- **설명**: 국가 신분증(CNI) 번호. 1995년-2021년 발급된 구형 CNI 는 12자리 숫자(`YY` 발급 연도 + `DD` 데파르트망 + `CCC` 코뮌 + 순번 5자리 구조로 알려짐, 확인 필요)이고, 2021년 3월 시범 발급을 거쳐 8월부터 전국 발급되는 신형 CNIe(신용카드 크기)는 9자리 영숫자(예: `D2H6862M2`)이다. 신형 번호의 자리별 문자 집합은 확인하지 못했다.
  - 예시: `950275123456` (구형 형식 예시), `D2H6862M2` (신형 형식 예시. 구조 미확인)
- **법적 근거**:
  - 법령: GDPR 제4조·제87조, LIL, Décret n° 55-1397 (CNI), Code pénal 제226-16조 이하
  - 감독기관: CNIL, 내무부 (ANTS)
  - 노출 금지 이유: 프랑스에서 가장 널리 쓰이는 신분증이며, 번호 + 이름 + 생년월일 조합이 은행·통신 계약과 본인확인에 쓰인다.
- **결정론적 검출 가능성**: 가능하나 정밀도가 낮다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{12}` | `950275123456` | **score 사용 필요**. 12자리 숫자열. 체크섬 없음 |
    | `[0-9A-Z]{9}` | `D2H6862M2` | **score 사용 필요**. 9자리 영숫자는 여권·운전면허·제품 코드와 광범위하게 겹친다. 자리별 문자 집합이 확인되면 좁힌다 |

    오탐: 높다. `boundary_check: true` 적용.
  - **byte-scan handwritten**: 구조 확인 후 판단.
  - **Aho-Corasick**: 부적합.
  - **권장**: 점수 체계 도입 후 낮은 `score` 로 등록. 신형 구조가 확인되면 패턴을 좁힌다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 구형은 체크섬 없음. 신형은 MRZ 체크 디지트가 있으나 번호 단독 등장 시 적용 불가.
- **채택 여부 및 근거**: 조건부 채택. 핵심 신분증이지만 두 형식 모두 검증기가 없고 오탐이 높아, 점수 체계 도입과 신형 구조 확인이 조건이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `carte d'identité`, `carte nationale d'identité`, `pièce d'identité`, `numéro cni`, `identity card`. (`cni` 단독은 3글자라 제외한다.)

### fr_driver_license

- **설명**: 운전면허번호. 2013년 9월 이후 카드형 면허증은 9자리 영숫자(숫자 2 + 영문 2 + 숫자 5, 여권과 같은 형태로 알려짐)이고, 구형 분홍색 3단 면허증은 12자리 숫자로 알려져 있으나 두 형식 모두 공식 명세를 확인하지 못했다(확인 필요).
  - 예시: `13AA00002` (카드형 형식 예시), `123456789012` (구형 형식 예시). 구조 미확인이라 검증하지 않았다.
- **법적 근거**:
  - 법령: Code de la route 제L.225-1조 이하 (운전면허 국가 파일 SNPC), GDPR 제4조
  - 감독기관: 내무부 (ANTS), CNIL
  - 노출 금지 이유: 신분증 대용으로 쓰이며 국가 운전면허 파일과 연결된다.
- **결정론적 검출 가능성**: 가능하나 형식이 확인되지 않았다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{2}[A-Z]{2}[0-9]{5}` | `13AA00002` | **score 사용 필요**. 여권 패턴과 동일하므로 같은 값이 두 recognizer 에 동시에 매치된다. 구조 확인 전에는 등록하지 않는다 |
    | `[0-9]{12}` | `123456789012` | **score 사용 필요**. 구형 CNI 패턴과 동일 |

  - **byte-scan handwritten**: 구조 확인 후 판단.
  - **Aho-Corasick**: 부적합.
  - **권장**: 형식 명세 확인 후 결정. 그 전에는 등록하지 않는다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 확인 필요.
- **채택 여부 및 근거**: 조건부 채택. 형식 명세 확인이 조건이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `permis de conduire`, `permis`, `numéro de permis`, `driver's license`, `driving licence`

### fr_iban

- **설명**: 프랑스 IBAN 과 RIB. IBAN 은 `FR` + 키 2자리 + BBAN 23자리 = 27자리이며, BBAN 은 RIB(relevé d'identité bancaire) 구조 `은행 코드 5 + 지점 코드 5 + 계좌번호 11(영숫자 가능) + RIB 키 2` 이다. 즉 프랑스 계좌번호는 IBAN 의 mod 97 키와 RIB 의 mod 97 키를 **둘 다** 갖는다. 서면에서는 `FR76 3000 6000 0112 3456 7890 189` 처럼 4자리씩 띄어 쓰고, RIB 는 `30006 00001 12345678901 89` 처럼 쓴다.
  - 예시: `FR1420041010050500013M02606`, `FR14 2004 1010 0505 0001 3M02 606` (ISO 13616 IBAN 레지스트리의 프랑스 견본. 계좌번호에 영문자 `M` 이 있으며 mod 97 과 RIB 키 `06` 을 모두 통과한다), `FR76 3000 6000 0112 3456 7890 189` (널리 쓰이는 견본. mod 97 과 RIB 키 `89` 통과), RIB 표기 `30006 00001 12345678901 89`
- **법적 근거**:
  - 법령: CMF 제L.511-33조 (은행 비밀), GDPR 제4조, Code pénal 제226-16조 이하
  - 감독기관: ACPR, Banque de France, CNIL
  - 노출 금지 이유: IBAN 만으로 SEPA 자동이체 위조가 가능하고, 프랑스는 급여·임대료·공과금 대부분이 RIB 제출로 처리되어 유출 빈도가 높다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `FR[0-9]{2} ?[0-9]{4} ?[0-9]{4} ?([0-9A-Z]{4} ?){3}[0-9A-Z][0-9]{2}` | `FR1420041010050500013M02606`, `FR14 2004 1010 0505 0001 3M02 606`, `FR7630006000011234567890189`, `FR76 3000 6000 0112 3456 7890 189` (26자리, `DE89…` 은 거부) | 기본. `FR` 접두 + 27자리 + `iban` 검증기. 자리 구조는 `FR`+키 2(그룹 1) / 은행 5+지점 5(그룹 2-3 과 그룹 4 첫 두 자리) / 계좌 11(영숫자, 그룹 4 뒤 두 자리부터 그룹 7 첫 자리까지) / RIB 키 2(숫자만)이다. 계좌 11자리에 영문자가 올 수 있으므로 그룹 4-7 을 영숫자로 두고, RIB 키 2자리는 숫자로 고정했다. `boundary_check: true` 적용 |
    | `[0-9]{5} ?[0-9]{5} ?[0-9A-Z]{11} ?[0-9]{2}` (RIB 단독 표기) | `30006 00001 12345678901 89`, `30006000011234567890189` | score 사용 고려. 구분자 없는 23자리는 다른 숫자열과 겹칠 수 있으나 `fr_rib` 검증기(1/97)로 보완된다 |

    오탐: IBAN 은 낮고, RIB 단독은 검증기 병행 시 낮다.
  - **byte-scan handwritten**: 가능하나 이득이 없다.
  - **Aho-Corasick**: 공통 IBAN detector 로 확장하면 적합(de_DE 문서 참조). `FR` 2바이트 anchor 를 국가 코드 목록의 하나로 등록한다.
  - **권장**: 공통 `iban` recognizer + `iban` 검증기. RIB 단독 표기와 `fr_rib` 검증기는 프랑스 고유이므로 `fr_iban` 항목에 남긴다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: (1) `iban`: ISO 7064 mod 97-10 (de_DE 문서와 동일). (2) `fr_rib`: RIB 키. 계좌번호의 영문자를 `A`-`I`→1-9, `J`-`R`→1-9, `S`-`Z`→2-9 로 바꾼 뒤 `97 - ((89 × 은행 + 15 × 지점 + 3 × 계좌) mod 97)` 이 키 2자리와 같으면 유효하다. IBAN 매치에도 BBAN 부분에 `fr_rib` 를 추가 적용할 수 있어 이중 검증이 된다.
- **채택 여부 및 근거**: 조건부 채택. IBAN 부분은 공통 항목으로 이관하고, RIB 단독 표기와 `fr_rib` 검증기는 프랑스 고유로 유지한다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `iban`, `relevé d'identité bancaire`, `compte bancaire`, `virement`, `prélèvement`, `sepa`, `banque`, `coordonnées bancaires`. (`rib` 은 `distribution`·`tribunal` 에, `bic` 은 3글자라 ` rib `·` bic ` 처럼 공백 포함 형태로 쓰거나 제외한다.)

### fr_phonenumber

- **설명**: 프랑스 전화번호. 국가번호 `+33`, 국내 형식은 `0` + 9자리 = 10자리 고정이며 `0X XX XX XX XX` 로 2자리씩 띄어 쓴다. 첫 두 자리 `01`-`05` 는 지역 유선, `06`·`07` 은 휴대전화, `08` 은 특수 요금, `09` 는 인터넷 전화이다. 국제 표기는 `+33 6 12 34 56 78` 처럼 `0` 을 뺀다.
  - 예시: `06 12 34 56 78`, `+33 6 12 34 56 78`, `06.12.34.56.78`, `0612345678`, `01-23-45-67-89`, `+33612345678`. 모두 형식 예시이다.
- **법적 근거**:
  - 법령: GDPR 제4조, CPCE 제L.34-1조 (가입자 데이터), 제L.34-5조 (동의 없는 전자 광고 금지), Bloctel 제도 (Code de la consommation 제L.223-1조)
  - 감독기관: ARCEP, CNIL
  - 노출 금지 이유: 휴대전화번호는 2단계 인증과 메신저 계정의 열쇠이고, 프랑스는 텔레마케팅 규제(Bloctel)가 강해 번호 유출 자체가 제재 사유가 된다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `(\+33 ?\|0)[1-9]([ .-]?[0-9]{2}){4}` | `06 12 34 56 78`, `+33 6 12 34 56 78`, `06.12.34.56.78`, `0612345678`, `01-23-45-67-89`, `+33612345678` (`00 12 34 56 78`, 9자리는 거부) | score 사용 고려. 10자리 고정 길이와 `0[1-9]` 접두가 필터이지만, 구분자 없는 `0612345678` 은 다른 10자리 숫자열과 겹친다. `boundary_check: true` 적용 |

    오탐: 중간. 독일과 달리 길이가 고정이라 유선·휴대전화를 한 패턴으로 다룰 수 있다. 한계: 프랑스에서 흔한 `+33 (0)6 12 34 56 78` 과 `0033 6 12 34 56 78` 표기는 잡지 못한다. 허용하려면 접두 대안에 `\+33 ?\(0\)` 과 `0033 ?` 를 추가한다.
  - **byte-scan handwritten**: 가능하나 단일 패턴이라 이득이 없다.
  - **Aho-Corasick**: 부분적으로 가능. `+33` 은 3바이트 anchor 로 적합하지만 국내 표기 `06`·`07` 은 2바이트라 흔하다. `kr_phonenumber` 의 `010` 처럼 강한 접두가 없으므로 regex 를 권장한다.
  - **권장**: regex.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 접두 표(`01`-`09`) 외 규칙 없음. 필요하면 `08` 특수 요금 번호를 제외하는 규칙을 검증기로 둘 수 있다.
- **채택 여부 및 근거**: 채택. 형식이 고정이라 오탐이 제어 가능하고 CPCE 가 보호한다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `téléphone`, `telephone`, `portable`, `mobile`, `appeler`, `joignable`, `phone`. (`tel`·`sms` 는 3글자, `numéro` 는 프랑스어 문장에서 극히 흔해 가산 근거로 약하므로 제외한다.)

### fr_vehicle_plate

- **설명**: 차량 번호판. 2009년 4월 도입된 SIV 형식은 `AA-123-AA`(대문자 2 + 숫자 3 + 대문자 2, 문자에서 `I`·`O`·`U` 제외, `SS` 조합 제외)로 전국 통일이고 차량 평생 불변이다. 2009년 이전 FNI 형식은 `1234 AB 75`(숫자 1-4 + 문자 1-3 + 데파르트망 2-3자리)이며 아직 도로에 남아 있다.
  - 예시: SIV `AB-123-CD`, `ZZ-999-ZY`. FNI `1234 AB 75`, `123 ABC 2A`, `1 A 974`. 모두 형식 예시이다.
- **법적 근거**:
  - 법령: Code de la route 제L.330-2조 (SIV 정보 접근 조건), 2009년 2월 9일 SIV 아레테, GDPR 제4조. CNIL 은 번호판을 소유자와 결합 가능한 개인정보로 본다(대시캠·주차 관리 관련 CNIL 지침).
  - 감독기관: 내무부 (ANTS), CNIL
  - 노출 금지 이유: 번호판으로 SIV 에서 소유자 정보를 조회할 수 있고(제L.330-2조의 조건 하에), 주차·통행 기록과 결합하면 위치 추적이 가능하다. 공개 노출되는 번호라 단독 위험도는 낮다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[A-HJ-NP-TV-Z]{2}-[0-9]{3}-[A-HJ-NP-TV-Z]{2}` | `AB-123-CD`, `ZZ-999-ZY` (`AI-123-CD`(I 포함), `AB-12-CD`, 공백 구분 `AB 123 CD` 는 거부) | 기본. 하이픈 구분 `2-3-2` 구조와 문자 집합 제한으로 오탐이 매우 낮다. `SS` 조합 제외는 regex 로 표현하기 번거로워 생략(오탐에 영향 없음). 공백 구분 표기를 허용하려면 `[- ]` 로 완화 |
    | `[0-9]{1,4} ?[A-Z]{1,3} ?(2A\|2B\|[0-9]{2,3})` | `1234 AB 75`, `123 ABC 2A`, `1 A 974` | **score 사용 필요**. 구형 FNI. `숫자 + 대문자 + 숫자` 는 `12 RUE 75`, `15 MAI 24`, `10 KM 200`, `4 ESC 12` 같은 프랑스어 주소·날짜·단위 표기와 그대로 겹친다(Python 으로 확인). 점수 체계 도입 전에는 등록하지 않는다. `boundary_check: true` 적용 |

  - **byte-scan handwritten**: 가능하나 이득이 없다.
  - **Aho-Corasick**: 부적합. 고정 접두가 없다.
  - **권장**: SIV 는 regex 기본 점수, FNI 는 점수 체계 도입 후 낮은 `score`.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 체크섬 없음. SIV 문자 집합은 regex 에 포함된다.
- **채택 여부 및 근거**: 채택. SIV 형식은 오탐이 매우 낮고 CNIL 이 개인정보로 본다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `immatriculation`, `plaque`, `plaque d'immatriculation`, `véhicule`, `vehicule`, `voiture`, `carte grise`, `license plate`. (`siv` 는 `exclusive` 등에 포함되므로 제외한다.)

### fr_siren_siret

- **설명**: SIREN 은 INSEE 가 모든 사업체(법인·개인사업자)에 부여하는 9자리 번호, SIRET 은 SIREN + 사업장 번호(NIC) 5자리 = 14자리이다. 둘 다 Luhn 체크섬을 따른다(La Poste 의 SIRET 만 예외). `123 456 782`, `123 456 782 00002` 처럼 3자리씩 띄어 쓴다.
  - 예시: `123 456 782`, `123456782` (Luhn 통과, 형식 예시), SIRET `12345678200002` (Luhn 통과, 형식 예시)
- **법적 근거**:
  - 법령: Code de commerce, Décret n° 73-314 (Sirene 저장소). INSEE Sirene 는 **공개 데이터**(open data)로 누구나 조회·다운로드할 수 있다.
  - 감독기관: INSEE
  - 노출 금지 이유: 약하다. 공개가 원칙인 번호이다. 다만 개인사업자(auto-entrepreneur)의 SIREN 은 개인 이름·주소와 함께 공개되어, INSEE 가 개인사업자의 부분 비공개 신청(diffusion partielle. 제도 전환 시점은 2022-2023년경으로 확인 필요)을 받는다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{3} ?[0-9]{3} ?[0-9]{3}` | `123 456 782`, `123456782` | score 사용 고려. 9자리 숫자열이지만 기존 `luhn` 검증기로 1/10 로 준다. 미채택 항목 |
    | `[0-9]{3} ?[0-9]{3} ?[0-9]{3} ?[0-9]{5}` | `123 456 782 00002`, `12345678200002` | score 사용 고려. 14자리 + `luhn`. 미채택 항목 |

  - **byte-scan handwritten**: 가능하나 이득이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: (채택 시) regex + 기존 `luhn` 검증기. 검증기 추가 구현이 필요 없다.
- **검증기**:
  - 현재: `luhn` 이 존재하며 그대로 적용 가능하다(숫자만 걸러 계산하므로 공백 표기도 처리된다). 단 La Poste(SIREN `356000000`)의 SIRET 은 Luhn 이 아니라 자릿수 합이 5의 배수인 규칙을 쓰므로 기존 `luhn` 이 거부한다.
  - 구현 가능: 추가 구현 불필요.
- **채택 여부 및 근거**: 미채택 (보류). 공개 데이터이므로 마스킹 대상으로 보기 어렵다. 개인사업자 보호 요구가 생기면 기존 `luhn` 으로 즉시 도입할 수 있다.
- **기존 구현 여부**: 신규 (미채택이므로 구현하지 않음)
- **context_words 후보** (재검토 시 참고): `siren`, `siret`, `numéro siret`, `kbis`, `entreprise`, `auto-entrepreneur`

| Numéro d'allocataire CAF (7자리) | CSS | 7자리 숫자만으로 구분 불가하다. |
| INS (Identifiant National de Santé) | CSP 제L.1111-8-1조 | NIR 과 동일한 번호이므로 `fr_nir` 이 담당한다. |
| Titre de séjour 번호 (10자리 영숫자) | CESEDA | 형식 명세를 확인하지 못했고 10자리 영숫자는 오탐이 많다. 이민 신분 노출 위험은 인정한다. |
| Numéro de mutuelle (민간 보험 가입자 번호) | CSP | 보험사마다 형식이 다르다. |
| Code postal (5자리) | GDPR | 5자리 숫자는 다른 숫자열과 구분되지 않는다. |
| 주소, 이름, 생년월일 | GDPR 제4조 | 국가 종속 항목이 아니며 regex 로 결정론적 검출이 불가능하다. 공통 항목 또는 NER 로 다룬다. |
| 생체정보, 건강 상태, 종교·노조 가입 | GDPR 제9조, LIL 제6조 | 특수 범주이지만 번호 형태로 나타나지 않는다. |
| 신용카드번호, 이메일, IP 주소 | GDPR, PCI DSS | 국가 종속 항목이 아니므로 이 문서 범위 밖이다. 기존 `card_number` 등이 담당한다. |

## 5. 구현 시 후속 작업 요약

이 문서에서 도출된, YAML·`validator.rs`·`handwritten/`·엔진에 반영할 작업 목록이다. 검증기는 **함수 구현 → YAML 등록** 순서를 지킨다(`validator::validate` 가 fail-open 이므로 순서가 바뀌면 검증 없이 통과한다).
