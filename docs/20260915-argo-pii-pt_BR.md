# PII 목록: pt_BR (브라질)

이 문서는 `tinicore/src/guardrails/config/pii_filter_config.yaml` 에 브라질(pt_BR) 고유 PII recognizer 가 포함되어야 하는 근거를 기록한다. 이미 YAML 에 있는 항목도 근거를 남기기 위해 포함하며, 국가에 종속되지 않는 항목(카드번호, API 키, 비밀번호, 이메일, IP 주소 등)은 다루지 않는다. 2026-09-15 현재 YAML 에 `br_*` recognizer 는 하나도 없으므로 이 문서의 모든 항목은 신규이다. `pii_type` 접두는 ISO 3166 국가 코드에 맞춰 `br_` 를 쓴다(locale 은 pt_BR).

## 0. 문서 작성 기준

각 항목은 다음 네 가지 기준으로 평가한다.

1. 적용 법령 또는 감독기관 규제상 노출되면 안 되는 PII 인가?
2. 그 PII 가 무엇이며, 노출을 막아야 하는 근거는 무엇인가?
3. 결정론적 방법(regex 또는 손으로 작성한 패턴 매칭)으로 검출할 수 있는가?
4. 검증기(체크섬 등)가 있어서 매칭 정확도를 높일 수 있는가? 검증기가 없어도 보안상 중요하면 채택한다.

### 검출 방식 세 가지 (결정론적 검출 가능성 항목에서 사용하는 용어)

엔진(`recognizer.rs` 의 `PiiEngine`)은 세 가지 매칭 방식을 지원하며, 어느 방식으로 찾은 매치든 같은 후처리 파이프라인(boundary check → validator → dedup → 점수 계산·임계값)을 거친다. 따라서 검증기와 context_words 는 방식과 무관하게 동일하게 적용된다.

| 방식 | 구현 위치 | 동작 | 적합한 경우 | 비용 |
|---|---|---|---|---|
| **regex** | `PatternRecognizer`, `PatternTemplateRecognizer` | 패턴을 30개 단위 청크(`DEFAULT_CHUNK_SIZE`)로 나눠 `regex_automata::hybrid::dfa`(lazy DFA)로 컴파일하고, 청크마다 텍스트를 한 번씩 스캔 | 패턴 수가 적고 구조가 단순할 때. 기본 선택지 | 패턴 수와 복잡도에 비례해 DFA 캐시 메모리와 스캔 횟수가 늘어난다. 카드번호는 105개 패턴이 문제가 되어 handwritten 으로 옮겼다 |
| **byte-scan handwritten** | `handwritten/card_detector.rs` 방식 (`MatchEngine` 직접 구현) | 텍스트를 바이트 단위로 걸으며 숫자열·영숫자열을 뽑고, 접두 표·길이·자리 규칙을 코드로 검사 | 접두가 고정 문자열이 아니라 **표**(BIN 처럼 여러 접두 구간)이거나, 주별 형식처럼 패턴 수가 많거나, 체크섬을 매칭 단계에서 바로 적용하고 싶을 때 | 메모리 거의 없음. 타입마다 detector 코드를 작성해야 한다 |
| **Aho-Corasick handwritten** | `handwritten/aho_corasick_detector.rs` (`pattern_desc_for` 에 anchor + verifier 등록) | 고정 문자열 anchor 를 하나의 automaton 으로 찾고, anchor 뒤의 바이트를 verifier 함수가 검사 | **고정 리터럴 접두**가 있고 그 뒤에 단순한 문자 집합 run 이 이어질 때 (`AKIA`, `ghp_`, `010` 등). 여러 타입을 한 automaton 에 묶어 텍스트를 한 번만 스캔한다 | 메모리 거의 없음. anchor 가 짧으면(1-2바이트) 텍스트 곳곳에서 verifier 가 호출되어 이득이 줄고, anchor 는 대소문자를 구분한다(`ascii_case_insensitive` 미사용) |

각 항목의 "결정론적 검출 가능성"에서는 regex 를 기본으로 표로 기술하고, 그 아래에 handwritten(byte-scan, Aho-Corasick) 대안의 실현 가능성과 **오탐률이 regex 대비 어떻게 달라지는지**를 함께 적는다. 오탐률은 매칭 형식이 같으면 방식과 무관하게 같고, handwritten 이 매칭 단계에서 표 대조나 체크섬을 추가로 수행하거나 (카드번호처럼) 구분자 제약을 의도적으로 풀 때만 달라진다.

### 점수 체계와 context_words (정확도가 낮은 패턴에 반드시 적용)

**현재 코드에서 context_words 는 매치를 걸러내지 않는다.** `compute_score` (`recognizer.rs`)는 context 단어가 매치 주변 ±50자 안에 있으면 1.0, 없으면 0.5 를 돌려주고, 임계값 `SCORE_THRESHOLD` 도 0.5 이므로 context 단어가 없어도 모든 매치가 살아남는다. 점수는 겹침 해소(`detector.rs`)에서 어느 매치를 우선할지 정하는 데에만 쓰인다. 따라서 "context_words 가 있으니 오탐을 걸러준다"는 가정은 현재 성립하지 않는다.

이 문서의 regex 표에서 **"score 사용 필요"** 로 표시한 패턴은, 형식만으로는 정확도가 낮아서 context 단어 없이 매칭되면 오탐이 될 가능성이 높은 것들이다. 이런 패턴을 채택하려면 Presidio 와 같은 방식의 점수 체계가 먼저 있어야 한다.

- `RecognizerConfig` 와 `PatternMeta` 에 recognizer 단위 `score` 필드(기본값 0.5)를 추가한다.
- `compute_score` 를 "기본 점수 + context 가산" 방식으로 바꾸고 임계값 0.5 는 유지한다. 가산값은 **0.5** 를 권장한다. 그러면 기존 recognizer 의 context 매치 점수가 지금과 같은 1.0 으로 유지되어 `tinicore/tests/guardrails/filter_test.rs` 의 `score == 1.0` 단정 3건(5331, 5441, 5471행)이 그대로 통과한다. Presidio 기본값 0.35 를 쓰면 통과·탈락 결과는 같지만 점수가 0.85 로 바뀌어 이 테스트들을 갱신해야 한다.
- 기존 recognizer 는 모두 기본값 0.5 이므로 통과·탈락 결과가 바뀌지 않는다. `card_number` 와 Aho-Corasick 계열은 Luhn 과 고정 접두가 이미 강한 필터라서 `score` 를 지정할 필요가 없다. `PatternMeta` 를 통해 같은 파이프라인을 타지만 값이 기본이라 영향이 없다.
- 낮은 `score` 를 준 recognizer 에는 `context_words` 를 반드시 채워야 한다. `compute_score` 는 `context_words` 가 비어 있으면 가산 없이 기본 점수를 돌려주므로, 비워 두면 모든 매치가 탈락한다.
- 정확도가 낮은 패턴은 같은 `pii_type` 을 가진 별도 recognizer(예: `us_driver_license_numeric`)로 분리해 `score: 0.3` 처럼 낮게 준다. context 없이는 0.3 으로 탈락하고, context 가 있으면 0.8 로 통과한다. pid 가 패턴 단위이고 `PatternMeta` 가 recognizer 설정을 패턴마다 복제하므로, 패턴별 점수보다 recognizer 분리가 스키마 변경이 적다.

context_words 는 소문자 부분 문자열 검색이므로 `car`, `tin`, `ead`, `ach`, `aba` 같은 짧은 단어는 `card`, `routing`, `read` 안에서도 걸린다. 점수 체계를 도입하면 이런 단어가 가산의 근거가 되므로, 짧은 단어는 목록에서 빼거나 앞뒤에 공백을 포함한 형태로 등록해야 한다.

### 엔진 제약 (regex 작성 시 유의)

- lazy DFA 이므로 **lookahead·lookbehind·역참조를 쓸 수 없다.** 배제 규칙(예: SSN 의 `000`, `666`, `9xx` 지역번호 제외)은 regex 가 아니라 `validator.rs` 의 검증 함수로 구현하거나, handwritten detector 안에서 코드로 처리한다.
- 현재 `validator.rs` 에 존재하는 검증기는 `luhn`, `rrn`, `phonenumber` 세 가지뿐이다. `rrn` 은 자릿수만 확인하고 `phonenumber` 는 항상 `true` 를 돌려준다. 아래 "검증기" 필드에서 "현재"는 이 세 가지 기준이고, "구현 가능"은 새로 작성해야 하는 검증 논리를 뜻한다.
- **`validator::validate` 는 fail-open 이다.** 모르는 검증기 이름이 오면 `true` 를 돌려준다. 따라서 YAML 에 `ssn`, `aba_routing` 같은 이름을 먼저 적고 함수를 나중에 구현하면 경고 없이 모든 매치가 통과한다. 반드시 **검증기 구현 → YAML 등록** 순서로 작업한다.
- 단어 경계 처리는 `boundary_check` 와 `boundary_check_reject_before/after` 설정으로 한다. `config.rs` 의 `boundary_check_reject_before` 필드 주석은 패턴 안의 `(?-u:\b)` 대신 이 설정을 쓰도록 안내한다(DFA 상태 수 감소). handwritten detector 도 같은 설정을 따른다.
- `RecognizerConfig` 에 대소문자 무시 옵션이 없다. 소문자 입력까지 잡으려면 패턴 안에 `(?i)` 인라인 플래그를 넣거나 문자 클래스에 소문자를 포함해야 한다. 기존 `us_passport` 는 `[a-zA-Z]` 로 소문자를 허용하고, 이 문서의 운전면허 제안은 `[A-Z]` 만 쓴다. 구현 시 통일한다.

### regex 표의 형식

각 항목의 regex 는 다음 3열 표로 기술한다. 표에 실린 모든 regex 는 Python `re` 로 예시와의 매칭을 확인했다(`(?-u:\b)` 는 `\b` 로 치환, `boundary_check` 는 인접 문자 검사로 모사).

| regex | 매칭 예시 | 비고 (score 사용 필요 등) |
|---|---|---|

"비고" 열의 표기는 다음 뜻이다.
- **score 사용 필요**: 형식만으로는 정확도가 낮다. 점수 체계 도입 후 낮은 `score` 로 등록해서 context 단어가 있을 때만 통과시킨다. 신규 패턴은 점수 체계가 없는 동안 등록하지 않는다. 이미 YAML 에 있는 기존 recognizer(en_US 의 `us_passport` 등)는 예외로, 현재 상태(오탐 감수)로 유지하다가 점수 체계 도입 후 낮은 `score` 로 전환한다.
- **score 사용 고려**: 형식만으로는 정확도가 중간이다. 검증기가 있으면 기본 점수로 충분하고, 검증기가 없거나 검증기 없이 등록한다면 낮은 `score` 를 권장한다.
- **기본**: 형식 자체가 충분히 특이해서 기본 점수 0.5 로 등록해도 된다.


### 이 문서의 regex 검증 방법에 대한 보충

엔진은 DFA 를 `MatchKind::All` 로 빌드해 겹치는 모든 매치 끝을 보고한 뒤 boundary check 와 dedup 으로 가장 긴 것을 남긴다. 엔진이 `unicode(false)` 로 DFA 를 빌드하므로 포르투갈어 악상 문자는 문자 클래스에 넣을 수 없으나, 이 문서의 regex 는 모두 ASCII 만 쓴다. CPF·CNPJ·IBAN 의 체크섬은 python-stdnum 2.2 의 `stdnum.br.cpf`, `stdnum.br.cnpj`, `stdnum.iban` 구현과 대조했다. PIS/PASEP·유권자증(título de eleitor)·CNH·CNS·RG(상파울루) 의 체크섬은 stdnum 에 구현이 없어 공개 규칙으로 자체 계산했고, 각 항목에 확인 필요로 표시했다.

## 1. 적용 법령 및 감독기관

브라질은 2018년 일반 개인정보 보호법(Lei Geral de Proteção de Dados Pessoais, LGPD, Lei 13.709/2018)이 GDPR 형 포괄법으로 제정되어 2020년 시행되었고, 감독기관은 ANPD(Autoridade Nacional de Proteção de Dados)이다. LGPD 제5조는 개인정보와 민감 개인정보(건강·생체·인종·종교 등)를 정의하고, 제46조는 보안 조치, 제48조는 유출 통지를 규정한다. 브라질 법제의 특징은 **CPF(세금 번호)가 사실상 범용 국가 식별번호**라는 점이다. 2022년 Decreto 10.977 로 도입된 신형 국가 신분증(CIN)은 CPF 를 유일한 신분증 번호로 채택했고, 은행·통신·의료·전자상거래 모든 분야에서 CPF 를 요구한다. 따라서 CPF 가 이 문서의 최우선 채택 대상이고, 주별 RG·CNH(운전면허)·CNS(건강 카드)·유권자증·PIS 가 뒤를 잇는다.

| 법령 | 감독기관 | 적용 범위 요약 |
|---|---|---|
| Lei 13.709/2018 (LGPD) 제5조, 제11조, 제46조, 제48조 | ANPD (Autoridade Nacional de Proteção de Dados) | 개인정보·민감 개인정보 정의, 민감 정보 처리 조건, 보안 조치, 유출 통지 |

## 3. 항목별 상세

### br_cpf

- **설명**: CPF (Cadastro de Pessoas Físicas). 연방 국세청(RFB)이 모든 개인에게 부여하는 11자리 번호로 `123.456.789-09` 처럼 `3.3.3-2` 로 표기한다. 마지막 2자리는 각각 앞자리에 가중치를 곱해 합한 값의 mod 11 로 계산한 체크 디지트이다. 9번째 자리는 발급 지역(세무 관할 구역) 코드이다. 2022년 이후 신형 국가 신분증(CIN)의 번호로 채택되어 사실상 유일한 국가 식별번호이며, 은행·통신·처방전·전자상거래(Nota Fiscal)·항공권에 예외 없이 기재된다.
  - 예시: `123.456.789-09`, `12345678909` (브라질 행정 안내에서 관용적으로 쓰는 형식 예시. 체크 디지트 통과), `390.533.447-05` (형식 예시). 모두 python-stdnum 으로 확인했다. 같은 숫자 반복(`111.111.111-11`)은 산술적으로 체크 디지트를 통과하지만 발급되지 않는 번호이다.
- **법적 근거**:
  - 법령: LGPD 제5조 (개인정보), Decreto 10.977/2022 (CIN 의 단일 번호), Instrução Normativa RFB 2.172/2024, Lei 13.444/2017 (ICN)
  - 감독기관: ANPD, RFB
  - 노출 금지 이유: 브라질의 범용 식별자이다. CPF + 이름 + 생년월일 조합으로 계좌 개설·Pix 등록·신용 조회·대출 사기가 가능하며, 브라질은 CPF 유출에 따른 신원 도용 피해가 특히 크다. ANPD 는 CPF 유출을 고위험 사고로 본다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{3}\.?[0-9]{3}\.?[0-9]{3}-?[0-9]{2}` | `123.456.789-09`, `12345678909`, `390.533.447-05`, `123456789-09` (`123.456.789-0`, 10자리는 거부) | score 사용 고려. 구분자 없는 11자리 숫자열은 CNH·PIS·전화번호와 겹치므로 `br_cpf` 검증기(약 1/100) 병행이 사실상 필수. 검증기 없이 등록한다면 score 사용 필요. 구분자 조합(`123.456789-09` 등 혼합 표기)은 제한하지 않고 검증기로 보완한다. `boundary_check: true` 적용 |

    오탐: 검증기 없이는 높고, 검증기를 붙이면 낮다.
  - **byte-scan handwritten**: 가능. 오탐률은 regex + `br_cpf` 조합과 **동일**하다.
  - **Aho-Corasick**: 부적합. 고정 접두가 없다.
  - **권장**: regex + `br_cpf` 검증기.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 첫 번째 체크 디지트 `d1` 은 앞 9자리에 가중치 `10 9 8 7 6 5 4 3 2` 를 곱해 합한 값 s 에 대해 `(11 - s mod 11) mod 11 mod 10`, 두 번째 `d2` 는 앞 9자리에 가중치 `11 … 3` 을 곱한 합에 `2 × d1` 을 더한 값으로 같은 계산을 한다. 같은 숫자 11개 반복은 산술적으로 통과하므로 별도 배제한다. 검증기 `br_cpf` 로 구현한다(python-stdnum `br.cpf` 와 동일. 반복 배제는 추가).
- **채택 여부 및 근거**: 채택. 브라질의 최고 등급 식별자이며 검증기가 있다.
- **기존 구현 여부**: 신규
- **context_words 후보**: ` cpf ` (3글자라 공백 포함 형태), `cadastro de pessoas físicas`, `cadastro de pessoa física`, `número do cpf`, `receita federal`, `tax id`

### br_rg

- **설명**: RG (Registro Geral). 각 주의 신분증 발급 기관(Instituto de Identificação, DETRAN 등)이 발급하는 신분증 번호로, 주마다 자릿수(7-10자리)와 체크 디지트 규칙이 다르다. 상파울루는 `12.345.678-9` 형식으로 8자리 + mod 11 체크 디지트(`X` 가능)이다. 2022년부터 CIN(CPF 기반)으로 대체되는 중이지만 구 RG 는 유효 기간까지 통용된다.
  - 예시: `12.345.678-2`, `123456782`, `34.567.890-4`, `12.345.671-X` (상파울루 형식 예시. 자체 계산한 mod 11 체크 디지트를 통과한다. 다른 주 형식은 다루지 않았다)
- **법적 근거**:
  - 법령: Lei 9.454/1997, Decreto 10.977/2022, LGPD 제5조
  - 감독기관: 각 주 신분증 발급 기관, ANPD
  - 노출 금지 이유: CPF 와 함께 본인확인의 두 축이다. RG + CPF 조합이 계약·은행·통신 개통의 기준이다.
- **결정론적 검출 가능성**: 가능하나 주별 형식 차이로 정밀도가 낮다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{1,2}\.?[0-9]{3}\.?[0-9]{3}-?[0-9X]` | `12.345.678-2`, `123456782`, `34.567.890-4`, `12.345.671-X` | **score 사용 필요**. 구분자 없는 8-9자리 숫자열은(7자리·10자리 형식의 주는 이 regex 가 잡지 못하므로 의도적으로 제외) 다른 번호와 광범위하게 겹치고, 체크 디지트 규칙이 주마다 달라 단일 검증기로 보완할 수 없다. 점 표기(`12.345.678-2`)만 허용하면 오탐이 줄지만 재현율이 떨어진다. 점수 체계 도입 전에는 등록하지 않는다. `boundary_check: true` 적용 |

    오탐: 높다.
  - **byte-scan handwritten**: 주별 규칙 표를 코드로 두면 상파울루 외의 주도 검증할 수 있으나 규칙 수집이 선행되어야 한다.
  - **Aho-Corasick**: 부적합.
  - **권장**: 점수 체계 도입 후 낮은 `score` 로 등록. 상파울루 mod 11 은 `br_rg_sp` 검증기로 선택 적용.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 상파울루는 앞 8자리에 가중치 `2 3 4 5 6 7 8 9` 를 곱해 합한 값 s 에 대해 `11 - s mod 11` 이 체크 디지트(10 이면 `X`, 11 이면 `0`)와 같으면 유효하다(확인 필요). 다른 주는 규칙 확인 필요.
- **채택 여부 및 근거**: 채택하되 점수 체계 도입이 선행 조건이다. 핵심 신분증이지만 주별 형식 차이로 검증기가 부분적이고 오탐이 높다.
- **기존 구현 여부**: 신규
- **context_words 후보**: ` rg ` (2글자라 공백 포함 형태), `registro geral`, `identidade`, `carteira de identidade`, `documento de identidade`, ` ssp ` (3글자라 공백 포함 형태)

### br_cnh

- **설명**: CNH (Carteira Nacional de Habilitação) 등록번호. SENATRAN 이 부여하는 11자리 번호로 마지막 2자리가 체크 디지트이다. 첫 번째 체크 디지트 `d1` 은 앞 9자리에 가중치 `9 … 1` 을 곱한 합의 mod 11 이며, 10 이상이면 `0` 으로 하고 보정값 2 를 기억한다. 두 번째 `d2` 는 가중치 `1 … 9` 를 곱한 합의 mod 11 에서 보정값(0 또는 2)을 뺀 값이며, 음수이면 11 을 더하고 10 이상이면 `0` 으로 한다. 이 규칙은 공식 문서로 공개된 것이 아니라 커뮤니티가 역산한 것이며 구현마다 음수 처리가 달라, 확인 필요이다. 디지털 면허증(CNH Digital)에도 같은 번호가 실린다.
  - 예시: `12345678900`, `24681357982` (형식 예시. 위 규칙으로 계산한 체크 디지트를 통과하며, 두 값 모두 보정값이 0 이라 구현 간 차이의 영향을 받지 않는다)
- **법적 근거**:
  - 법령: CTB 제140조 이하, LGPD 제5조
  - 감독기관: SENATRAN, 각 주 DETRAN, ANPD
  - 노출 금지 이유: 사진 신분증으로서 RG 와 같은 효력을 가지며, 번호로 DETRAN 기록(벌점·주소)이 조회된다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{11}` | `12345678900`, `24681357982` | score 사용 고려. 11자리 숫자열은 CPF·PIS·전화번호와 겹치므로 `br_cnh` 검증기(약 1/100) 병행이 사실상 필수. 검증기 없이 등록한다면 score 사용 필요. CPF 검증기와 CNH 검증기를 모두 통과하는 값은 드물다. `boundary_check: true` 적용 |

    오탐: 검증기 없이는 매우 높고, 검증기를 붙이면 낮다.
  - **byte-scan handwritten**: 가능. 오탐률은 regex + `br_cnh` 조합과 **동일**하다.
  - **Aho-Corasick**: 부적합.
  - **권장**: regex + `br_cnh` 검증기.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 위 이중 mod 11 규칙. 검증기 `br_cnh` 로 구현하되, 공식 명세가 없으므로 실제 발급 번호 표본으로 규칙(특히 보정값·음수 처리)을 확인한 뒤 구현한다.
- **채택 여부 및 근거**: 채택. 신분증 번호이며 검증기가 있다(규칙 확인 필요).
- **기존 구현 여부**: 신규
- **context_words 후보**: ` cnh ` (3글자라 공백 포함 형태), `carteira de habilitação`, `carteira de motorista`, `habilitação`, `registro da cnh`, `detran`

### br_pis

- **설명**: PIS/PASEP/NIT 번호(통칭 NIS). 사회보장·노동 기록의 가입번호로 11자리이며 `123.45678.90-0` 형식으로 표기한다. 마지막 자리는 앞 10자리에 가중치 `3 2 9 8 7 6 5 4 3 2` 를 곱한 합의 mod 11 로 계산한 체크 디지트이다. 노동 수첩(CTPS)·급여명세서·FGTS 기록에 기재된다.
  - 예시: `123.45678.90-0`, `12345678900`, `200.12345.67-3` (형식 예시. 위 규칙으로 계산한 체크 디지트를 통과한다)
- **법적 근거**:
  - 법령: Lei 8.212/1991, Decreto 3.048/1999, LGPD 제5조
  - 감독기관: INSS, Caixa Econômica Federal, ANPD
  - 노출 금지 이유: 고용·연금·FGTS·복지 급여의 연결 키이다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{3}\.?[0-9]{5}\.?[0-9]{2}-?[0-9]` | `123.45678.90-0`, `12345678900`, `200.12345.67-3` | score 사용 고려. 구분자 없는 11자리는 CPF·CNH 와 같은 형식이므로 `br_pis` 검증기(1/11) 병행이 사실상 필수. 예시 `12345678900` 은 CNH 예시와 같은 값이며 두 검증기를 모두 통과한다. `boundary_check: true` 적용 |

    오탐: 검증기 없이는 높고, 검증기를 붙이면 중간이다.
  - **byte-scan handwritten**: 가능. 오탐률은 regex + `br_pis` 조합과 **동일**하다.
  - **Aho-Corasick**: 부적합.
  - **권장**: regex + `br_pis` 검증기.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 위 가중합 mod 11(`11 - r` 이 10 이상이면 0). 검증기 `br_pis` 로 구현한다(확인 필요).
- **채택 여부 및 근거**: 채택. 사회보장 기록의 연결 키이고 검증기가 있다.
- **기존 구현 여부**: 신규
- **context_words 후보**: ` pis ` , ` nis `, ` nit ` (3글자라 공백 포함 형태), `pis/pasep`, `pasep`, `número de identificação social`, `ctps`, `fgts`, `inss`

### br_voter_id

- **설명**: Título de eleitor(유권자증) 번호. TSE 가 부여하는 12자리 번호로 일련번호 8자리 + 주(UF) 코드 2자리(`01`-`28`) + 체크 디지트 2자리 구조이며 `1234 5678 0191` 처럼 4-4-4 로 띄어 쓴다. 체크 디지트는 각각 mod 11 로 계산하며 상파울루(`01`)·미나스제라이스(`02`)는 나머지 0 을 1 로 바꾸는 예외가 있다(공개 자료 기준, 확인 필요).
  - 예시: `1234 5678 0191`, `123456780191`, `8765 4321 1929` (형식 예시. 위 규칙으로 계산한 체크 디지트를 통과한다)

- **context_words 후보**: `placa`, `placa do carro`, `placa do veículo`, `veículo`, `veiculo`, `renavam`, `carro`, `license plate`

### br_cnpj

- **설명**: CNPJ (Cadastro Nacional da Pessoa Jurídica). RFB 가 법인·사업체에 부여하는 14자리 번호로 `16.727.230/0001-97` 형식(`2.3.3/4-2`: 본점 식별 8 + 지점 4 + 체크 2)이다. 2026년 7월부터 신규 번호는 영숫자 형식으로 전환된다(Instrução Normativa RFB 2.229/2024 가 IN 2.119/2022 를 개정. 확인 필요).
  - 예시: `16.727.230/0001-97`, `16727230000197` (python-stdnum 문서 예시. 체크 디지트 통과)
- **법적 근거**:
  - 법령: Instrução Normativa RFB 2.119/2022. RFB 조회 서비스에서 **공개** 확인되고 송장(Nota Fiscal)·간판·웹사이트에 기재가 의무이다.
  - 감독기관: RFB
  - 노출 금지 이유: 약하다. 공개 사업자 번호이다. 개인사업자(MEI)의 CNPJ 는 개인 이름과 함께 공개된다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{2}\.?[0-9]{3}\.?[0-9]{3}/?[0-9]{4}-?[0-9]{2}` | `16.727.230/0001-97`, `16727230000197` | score 사용 고려. 구분자 없는 14자리는 다른 번호와 겹칠 수 있으나 `br_cnpj` 검증기(약 1/100)로 좁힐 수 있다. 2026년 영숫자 형식은 별도 패턴 필요. 미채택 항목 |

  - **byte-scan handwritten**: 가능하나 이점이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: 미채택.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 이중 mod 11(python-stdnum `br.cnpj` 와 동일).
- **채택 여부 및 근거**: 미채택. 공개 사업자 번호이다. MEI 보호 요구가 생기면 재검토한다.
- **기존 구현 여부**: 신규 (미채택이므로 구현하지 않음)
- **context_words 후보** (재검토 시 참고): `cnpj`, `razão social`, `empresa`, ` mei ` (3글자라 공백 포함 형태. `meio`·`primeiro` 에 포함)

## 4. 검토 후 미채택한 항목

아래 항목은 법령상 PII 이거나 식별번호이지만 결정론적 검출이 불가능하거나 공개 번호라서 recognizer 로 등록하지 않는다.

| 항목 | 법적 근거 | 미채택 이유 |
|---|---|---|
| Pix 키 (CPF·전화·이메일·무작위 UUID) | Resolução BCB 1/2020 | CPF·전화·이메일 키는 각각의 recognizer 가 잡고, 무작위 키는 UUID 형식이라 다른 UUID 와 구분되지 않는다. |
| CEP (우편번호, `01310-100`) | 해당 없음 | `5-3` 하이픈 표기는 특이하지만 거리 구간 단위라 단독 식별력이 낮다. 주소 마스킹 정책과 함께 결정한다. |
| CTPS (노동 수첩) 번호, 예비군증(reservista) 번호 | CLT, Lei 4.375/1964 | 형식 명세가 없거나 주별로 다르다. PIS 가 노동 기록의 실질 키이다. |
| 출생·혼인 증명서 등록번호 (32자리 matrícula) | Lei 6.015/1973 | 형식은 결정론적(32자리)이나 일반 텍스트에 드물다. 필요 시 재검토. |
| RENAVAM (차량 등록번호, 11자리) | CTB | 차량 식별자이며 번호판으로 대체된다. mod 11 체크 디지트(가중치 `3 2 9 8 7 6 5 4 3 2`)가 있어 검출은 가능하나 번호판이 이미 채택되어 중복이다. |
| 주소, 이름, 생년월일 | LGPD 제5조 | 국가 종속 항목이 아니며 regex 로 결정론적 검출이 불가능하다. 공통 항목 또는 NER 로 다룬다. |
| 생체정보, 건강 상태, 인종·종교 | LGPD 제5조 제2호 | 민감 개인정보이지만 번호 형태로 나타나지 않는다. |
| 신용카드번호, 이메일, IP 주소 | LGPD, PCI DSS | 국가 종속 항목이 아니므로 이 문서 범위 밖이다. 기존 `card_number` 등이 담당한다. |

## 5. 구현 시 후속 작업 요약

이 문서에서 도출된, YAML·`validator.rs`·`handwritten/`·엔진에 반영할 작업 목록이다. 검증기는 **함수 구현 → YAML 등록** 순서를 지킨다(`validator::validate` 가 fail-open 이므로 순서가 바뀌면 검증 없이 통과한다).
