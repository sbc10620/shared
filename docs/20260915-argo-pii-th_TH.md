# PII 목록: th_TH (태국)

이 문서는 `tinicore/src/guardrails/config/pii_filter_config.yaml` 에 태국(th_TH) 고유 PII recognizer 가 포함되어야 하는 근거를 기록한다. 이미 YAML 에 있는 항목도 근거를 남기기 위해 포함하며, 국가에 종속되지 않는 항목(카드번호, API 키, 비밀번호, 이메일, IP 주소 등)은 다루지 않는다. 2026-09-15 현재 YAML 에 `th_*` recognizer 는 하나도 없으므로 이 문서의 모든 항목은 신규이다. `pii_type` 접두는 ISO 3166 국가 코드에 맞춰 `th_` 를 쓴다(locale 은 th_TH).

## 0. 문서 작성 기준

각 항목은 다음 네 가지 기준으로 평가한다.

1. 적용 법령 또는 감독기관 규제상 노출되면 안 되는 PII 인가?
2. 그 PII 가 무엇이며, 노출을 막아야 하는 근거는 무엇인가?
3. 결정론적 방법(regex 또는 손으로 작성한 패턴 매칭)으로 검출할 수 있는가?
4. 검증기(체크섬 등)가 있어서 매칭 정확도를 높일 수 있는가? 검증기가 없어도 보안상 중요하면 채택한다.

### 검출 방식 세 가지 (결정론적 검출 가능성 항목에서 사용하는 용어)

엔진(`recognizer.rs` 의 `PiiEngine`)은 세 가지 매칭 방식을 지원하며, 어느 방식으로 찾은 매치든 같은 후처리 파이프라인(boundary check → validator → dedup → 점수 계산·임계값)을 거친다. 따라서 검증기와 context_words 는 방식과 무관하게 동일하게 적용된다.

| 방식 | 구현 위치 | 동작 | 적합한 경우 | 비용 |
|---|---|---|---|---|
| **regex** | `PatternRecognizer`, `PatternTemplateRecognizer` | 패턴을 30개 단위 청크(`DEFAULT_CHUNK_SIZE`)로 나눠 `regex_automata::hybrid::dfa`(lazy DFA)로 컴파일하고, 청크마다 텍스트를 한 번씩 스캔 | 패턴 수가 적고 구조가 단순할 때. 기본 선택지 | 패턴 수와 복잡도에 비례해 DFA 캐시 메모리와 스캔 횟수가 늘어난다. 카드번호는 105개 패턴이 문제가 되어 handwritten 으로 옮겼다 |
| **byte-scan handwritten** | `handwritten/card_detector.rs` 방식 (`MatchEngine` 직접 구현) | 텍스트를 바이트 단위로 걸으며 숫자열·영숫자열을 뽑고, 접두 표·길이·자리 규칙을 코드로 검사 | 접두가 고정 문자열이 아니라 **표**(BIN 처럼 여러 접두 구간)이거나, 주별 형식처럼 패턴 수가 많거나, 체크섬을 매칭 단계에서 바로 적용하고 싶을 때 | 메모리 거의 없음. 타입마다 detector 코드를 작성해야 한다 |
| **Aho-Corasick handwritten** | `handwritten/aho_corasick_detector.rs` (`pattern_desc_for` 에 anchor + verifier 등록) | 고정 문자열 anchor 를 하나의 automaton 으로 찾고, anchor 뒤의 바이트를 verifier 함수가 검사 | **고정 리터럴 접두**가 있고 그 뒤에 단순한 문자 집합 run 이 이어질 때 (`AKIA`, `ghp_`, `010` 등). 여러 타입을 한 automaton 에 묶어 텍스트를 한 번만 스캔한다 | 메모리 거의 없음. anchor 가 짧으면(1-2바이트) 텍스트 곳곳에서 verifier 가 호출되어 이득이 줄고, anchor 는 대소문자를 구분한다(`ascii_case_insensitive` 미사용) |

각 항목의 "결정론적 검출 가능성"에서는 regex 를 기본으로 표로 기술하고, 그 아래에 handwritten(byte-scan, Aho-Corasick) 대안의 실현 가능성과 **오탐률이 regex 대비 어떻게 달라지는지**를 함께 적는다. 오탐률은 매칭 형식이 같으면 방식과 무관하게 같고, handwritten 이 매칭 단계에서 표 대조나 체크섬을 추가로 수행하거나 (카드번호처럼) 구분자 제약을 의도적으로 풀 때만 달라진다.

### 점수 체계와 context_words (정확도가 낮은 패턴에 반드시 적용)

**현재 코드에서 context_words 는 매치를 걸러내지 않는다.** `compute_score` (`recognizer.rs`)는 context 단어가 매치 주변 ±50자 안에 있으면 1.0, 없으면 0.5 를 돌려주고, 임계값 `SCORE_THRESHOLD` 도 0.5 이므로 context 단어가 없어도 모든 매치가 살아남는다. 점수는 겹침 해소(`detector.rs`)에서 어느 매치를 우선할지 정하는 데에만 쓰인다. 따라서 "context_words 가 있으니 오탐을 걸러준다"는 가정은 현재 성립하지 않는다.

이 문서의 regex 표에서 **"score 사용 필요"** 로 표시한 패턴은, 형식만으로는 정확도가 낮아서 context 단어 없이 매칭되면 오탐이 될 가능성이 높은 것들이다. 이런 패턴을 채택하려면 Presidio 와 같은 방식의 점수 체계가 먼저 있어야 한다.

- `RecognizerConfig` 와 `PatternMeta` 에 recognizer 단위 `score` 필드(기본값 0.5)를 추가한다.
- `compute_score` 를 "기본 점수 + context 가산" 방식으로 바꾸고 임계값 0.5 는 유지한다. 가산값은 **0.5** 를 권장한다. 그러면 기존 recognizer 의 context 매치 점수가 지금과 같은 1.0 으로 유지되어 `tinicore/tests/guardrails/filter_test.rs` 의 `score == 1.0` 단정 3건(5331, 5441, 5471행)이 그대로 통과한다. Presidio 기본값 0.35 를 쓰면 통과·탈락 결과는 같지만 점수가 0.85 로 바뀌어 이 테스트들을 갱신해야 한다.
- 기존 recognizer 는 모두 기본값 0.5 이므로 통과·탈락 결과가 바뀌지 않는다. `card_number` 와 Aho-Corasick 계열은 Luhn 과 고정 접두가 이미 강한 필터라서 `score` 를 지정할 필요가 없다. `PatternMeta` 를 통해 같은 파이프라인을 타지만 값이 기본이라 영향이 없다.
- 낮은 `score` 를 준 recognizer 에는 `context_words` 를 반드시 채워야 한다. `compute_score` 는 `context_words` 가 비어 있으면 가산 없이 기본 점수를 돌려주므로, 비워 두면 모든 매치가 탈락한다.
- 정확도가 낮은 패턴은 같은 `pii_type` 을 가진 별도 recognizer(예: `us_driver_license_numeric`)로 분리해 `score: 0.3` 처럼 낮게 준다. context 없이는 0.3 으로 탈락하고, context 가 있으면 0.8 로 통과한다. pid 가 패턴 단위이고 `PatternMeta` 가 recognizer 설정을 패턴마다 복제하므로, 패턴별 점수보다 recognizer 분리가 스키마 변경이 적다.

context_words 는 소문자 부분 문자열 검색이므로 `car`, `tin`, `ead`, `ach`, `aba` 같은 짧은 단어는 `card`, `routing`, `read` 안에서도 걸린다. 점수 체계를 도입하면 이런 단어가 가산의 근거가 되므로, 짧은 단어는 목록에서 빼거나 앞뒤에 공백을 포함한 형태로 등록해야 한다.

### 엔진 제약 (regex 작성 시 유의)

- lazy DFA 이므로 **lookahead·lookbehind·역참조를 쓸 수 없다.** 배제 규칙(예: SSN 의 `000`, `666`, `9xx` 지역번호 제외)은 regex 가 아니라 `validator.rs` 의 검증 함수로 구현하거나, handwritten detector 안에서 코드로 처리한다.
- 현재 `validator.rs` 에 존재하는 검증기는 `luhn`, `rrn`, `phonenumber` 세 가지뿐이다. `rrn` 은 자릿수만 확인하고 `phonenumber` 는 항상 `true` 를 돌려준다. 아래 "검증기" 필드에서 "현재"는 이 세 가지 기준이고, "구현 가능"은 새로 작성해야 하는 검증 논리를 뜻한다.
- **`validator::validate` 는 fail-open 이다.** 모르는 검증기 이름이 오면 `true` 를 돌려준다. 따라서 YAML 에 `ssn`, `aba_routing` 같은 이름을 먼저 적고 함수를 나중에 구현하면 경고 없이 모든 매치가 통과한다. 반드시 **검증기 구현 → YAML 등록** 순서로 작업한다.
- 단어 경계 처리는 `boundary_check` 와 `boundary_check_reject_before/after` 설정으로 한다. `config.rs` 의 `boundary_check_reject_before` 필드 주석은 패턴 안의 `(?-u:\b)` 대신 이 설정을 쓰도록 안내한다(DFA 상태 수 감소). handwritten detector 도 같은 설정을 따른다.
- `RecognizerConfig` 에 대소문자 무시 옵션이 없다. 소문자 입력까지 잡으려면 패턴 안에 `(?i)` 인라인 플래그를 넣거나 문자 클래스에 소문자를 포함해야 한다. 기존 `us_passport` 는 `[a-zA-Z]` 로 소문자를 허용하고, 이 문서의 운전면허 제안은 `[A-Z]` 만 쓴다. 구현 시 통일한다.

### regex 표의 형식

각 항목의 regex 는 다음 3열 표로 기술한다. 표에 실린 모든 regex 는 Python `re` 로 예시와의 매칭을 확인했다(`(?-u:\b)` 는 `\b` 로 치환, `boundary_check` 는 인접 문자 검사로 모사).

| regex | 매칭 예시 | 비고 (score 사용 필요 등) |
|---|---|---|

"비고" 열의 표기는 다음 뜻이다.
- **score 사용 필요**: 형식만으로는 정확도가 낮다. 점수 체계 도입 후 낮은 `score` 로 등록해서 context 단어가 있을 때만 통과시킨다. 신규 패턴은 점수 체계가 없는 동안 등록하지 않는다. 이미 YAML 에 있는 기존 recognizer(en_US 의 `us_passport` 등)는 예외로, 현재 상태(오탐 감수)로 유지하다가 점수 체계 도입 후 낮은 `score` 로 전환한다.
- **score 사용 고려**: 형식만으로는 정확도가 중간이다. 검증기가 있으면 기본 점수로 충분하고, 검증기가 없거나 검증기 없이 등록한다면 낮은 `score` 를 권장한다.
- **기본**: 형식 자체가 충분히 특이해서 기본 점수 0.5 로 등록해도 된다.


### 이 문서의 regex 검증 방법에 대한 보충

엔진은 DFA 를 `MatchKind::All` 로 빌드해 겹치는 모든 매치 끝을 보고한 뒤 boundary check 와 dedup 으로 가장 긴 것을 남긴다. 엔진이 `unicode(false)` 로 DFA 를 빌드하므로 태국 문자는 문자 클래스(`[ก-ฮ]`)에 넣을 수 없고 리터럴 대안(`(ก|ข|…)`)으로만 쓸 수 있다(ko_KR 문서의 한글 처리와 같은 이유. 태국 문자는 UTF-8 3바이트라 리터럴 대안이 컴파일된다). 또한 **`boundary_check` 는 ASCII 영숫자만 검사하므로 태국 문자 앞뒤 경계에는 아무 영향이 없고**, 태국어는 단어 사이에 공백을 두지 않으므로 태국 문자로 시작하는 패턴(번호판)은 문장 한가운데에서도 매치된다. 국민 ID·법인 등록번호의 체크섬은 python-stdnum 2.2 의 `stdnum.th.pin`, `stdnum.th.moa` 와 대조했다.

## 1. 적용 법령 및 감독기관

태국은 2019년 개인정보 보호법(Personal Data Protection Act B.E. 2562, PDPA)이 GDPR 형 포괄법으로 제정되어 2022년 6월 전면 시행되었고, 감독기관은 개인정보보호위원회(PDPC)와 그 사무국이다. PDPA 제26조는 인종·종교·건강·생체·범죄 기록 등을 민감 개인정보로 열거하고 명시적 동의를 요구한다. 태국 법제의 특징은 **13자리 국민 ID 번호(เลขประจำตัวประชาชน)가 세금·사회보장·건강보험·은행(PromptPay)·통신 가입의 단일 키**라는 점이다. 개인 납세자 번호(TIN)는 국민 ID 와 같고, 사회보장·보편적 건강보장(UCS)·PromptPay 송금도 국민 ID 를 식별자로 쓴다. 따라서 국민 ID 가 최우선 채택 대상이며, 여권·전화번호·계좌번호·번호판이 뒤를 잇는다.

| 법령 | 감독기관 | 적용 범위 요약 |
|---|---|---|
| Personal Data Protection Act B.E. 2562 (2019) 제6조, 제26조, 제37조 | PDPC (Personal Data Protection Committee), Office of the PDPC | 개인정보·민감 개인정보 정의, 보안 조치, 유출 통지 |
| Civil Registration Act B.E. 2534 (1991) 제16조; National Identity Card Act B.E. 2526 (1983, 2011년 개정) | 내무부 지방행정국 (Department of Provincial Administration, DOPA) | 13자리 국민 ID 번호의 부여와 국민 ID 카드 |
| Revenue Code 제3조 undecim; 국세청 고시 | 국세청 (Revenue Department) | 납세자 번호(개인은 국민 ID, 법인은 등록번호) |
| Social Security Act B.E. 2533 (1990); National Health Security Act B.E. 2545 (2002) | 사회보장청 (SSO), 국민건강보장청 (NHSO) | 사회보장·보편적 건강보장은 국민 ID 를 식별자로 사용 |
| 외무부 여권 발급 규정 (ระเบียบกระทรวงการต่างประเทศ ว่าด้วยการออกหนังสือเดินทาง พ.ศ. 2548. 태국에는 별도 여권법이 없음) | 외무부 영사국 | 여권 발급 |
| Motor Vehicle Act B.E. 2522 (1979) 제6조 이하, 제42조; Land Transport Act B.E. 2522 | 육상교통국 (Department of Land Transport, DLT) | 차량 등록·번호판, 운전면허 |
| Financial Institutions Business Act B.E. 2551 (2008) 제154조; BOT 규정 (PromptPay) | 태국 은행 (BOT) | 은행 정보 비밀, 계좌 식별자 |
| Telecommunications Business Act B.E. 2544 (2001); NBTC 규정 (SIM 등록) | 방송통신위원회 (NBTC) | 통신 가입자 정보, SIM 실명 등록(국민 ID 연계) |
| Computer Crime Act B.E. 2550 (2007, 2017년 개정) | 디지털경제사회부 (MDES) | 컴퓨터 시스템의 데이터 무단 접근·유출 처벌 |
| Civil and Commercial Code; Department of Business Development 규정 | 상무부 사업개발국 (DBD) | 법인 등록번호(13자리, `0` 시작)는 공개 사업자 번호 |

| th_bank_account | 은행 계좌번호 (10자리, `123-4-56789-0`) | 가능 (구분자 표기만) | regex | 없음 / 없음 | 사용 고려 (구분자 표기) / **사용 필요** (숫자만) | 신규 | 채택 (구분자 표기는 바로, 숫자만 형식은 점수 체계 도입이 선행 조건) |
| th_phonenumber (recognizer `th_phonenumber`) | 휴대전화번호 (`0[689]X`, 10자리) | 가능 | regex | 없음 / 통신사 접두 표 | 사용 고려 | 신규 | 채택 |
| th_phonenumber (recognizer `th_phonenumber_landline`) | 유선전화번호 (`02`·`0[3457]X`, 9자리) | 가능 | regex | 없음 / 지역번호 표 | 사용 고려 | 신규 | 채택 |
| th_vehicle_plate | 차량 번호판 (태국 문자 1-2자 + 숫자 1-4자리) | 가능 (약함) | regex (태국 문자 리터럴 대안) 또는 byte-scan (도 이름 동반 검사, 권장) | 없음 / 사용 자음 표, 도 이름 표 | **사용 필요** | 신규 | 조건부 채택 (점수 체계 도입이 선행 조건. 태국 문자 경계 문제) |
| th_company_id | 법인 등록번호 (13자리, `0` 시작) | 가능 | regex (+ `th_pin` 검증기 재사용) | 없음 / 가중합 mod 11 (국민 ID 와 동일) | 기본 | 신규 | 미채택 |

이외에 검토했으나 결정론적 검출이 불가능하거나 공개 번호라서 미채택한 항목은 4절에 정리했다.

## 3. 항목별 상세

### th_national_id

- **설명**: 국민 ID 번호(เลขประจำตัวประชาชน 13 หลัก). 내무부가 출생 시 또는 귀화 시 부여하는 13자리 번호로 `1-2345-67890-12-3` 처럼 `1-4-5-2-1` 로 띄어 쓴다. 첫 자리는 사람 유형(`1`·`2` 1984년 이후 출생 등록 태국인, `3` 1984년 이전 등록, `4` 등록 누락 후 추가 등록, `5` 지연 등록, `6` 외국인·소수민족, `7` 그 자녀(태국 출생), `8` 영주권자·귀화자. 코드 의미는 확인 필요), 2-5번째는 최초 등록 지역(도·군) 코드, 6-12번째는 일련번호, 13번째는 앞 12자리에 가중치 `13 … 2` 를 곱한 합의 mod 11 로 계산한 체크 디지트(`(11 - r) mod 10`)이다. 외국인 등록 카드(핑크 카드)는 `0` 으로 시작하는 13자리를 쓴다는 자료가 있다(확인 필요). 다만 `0` 시작 13자리 + 같은 체크 디지트 규칙은 법인 등록번호의 형식과 정확히 같고 python-stdnum 도 `0`·`9` 시작을 거부하므로, 핑크 카드를 포함하려면 검증기와 regex 를 함께 바꾸고 법인 번호와의 충돌을 감수해야 한다. 개인 납세자 번호·사회보장·건강보험·PromptPay·SIM 등록의 식별자이다.
  - 예시: `1101700001237`, `1-1017-00001-23-7`, `3 5001 01000 12 0` (형식 예시. python-stdnum 으로 체크 디지트 확인)
- **법적 근거**:
  - 법령: Civil Registration Act 제16조, National Identity Card Act, PDPA 제6조 (개인정보), Revenue Code 제3조 undecim (개인 TIN = 국민 ID)
  - 감독기관: DOPA, PDPC
  - 노출 금지 이유: 태국의 단일 국가 식별자이며 세금·사회보장·건강·은행·통신을 모두 관통한다. 국민 ID + 이름 + 생년월일로 대출·SIM 발급·PromptPay 사기가 가능하고, 태국은 콜센터 사기(แก๊งคอลเซ็นเตอร์)가 특히 많아 PDPC 가 국민 ID 유출을 중점 단속한다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[1-8][ -]?[0-9]{4}[ -]?[0-9]{5}[ -]?[0-9]{2}[ -]?[0-9]` | `1101700001237`, `1-1017-00001-23-7`, `3 5001 01000 12 0` (`0101…`(첫 자리 0), `9101…`, 12자리는 거부) | score 사용 고려. 구분자 없는 13자리 숫자열은 다른 번호와 겹치므로 `th_pin` 검증기(1/10) 병행이 사실상 필수. 검증기 없이 등록한다면 score 사용 필요. 구분자 표기(`1-4-5-2-1`)는 특이해서 오탐이 낮다. 외국인 핑크 카드를 포함하려면 첫 자리를 `[0-8]` 로 넓히고 `th_pin` 검증기도 `0` 을 허용하도록 바꿔야 하며, 그러면 법인 등록번호(`th_company_id`)가 모두 국민 ID 로 잡힌다(확인 필요). `boundary_check: true` 적용 |

    오탐: 검증기 없이는 높고, 검증기를 붙이면 중간이다.
  - **byte-scan handwritten**: 가능. 오탐률은 regex + `th_pin` 조합과 **동일**하다.
  - **Aho-Corasick**: 부적합. 첫 자리 한 글자뿐이다.
  - **권장**: regex + `th_pin` 검증기.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 앞 12자리에 가중치 `13 12 … 2` 를 곱해 합한 값 s 에 대해 `(11 - s mod 11) mod 10` 이 13번째 자리와 같으면 유효하다. 검증기 `th_pin` 으로 구현한다(python-stdnum `th.pin` 과 동일. 첫 자리 `9` 배제).
- **채택 여부 및 근거**: 채택. 태국의 최고 등급 식별자이며 검증기가 있다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `เลขประจำตัวประชาชน`, `เลขบัตรประชาชน`, `บัตรประชาชน`, `เลขประจำตัว`, `id card`, `national id`, `thai id`, `citizen id`

### th_passport

- **설명**: 태국 여권번호. 전자여권은 `대문자 1-2 + 숫자 7` 의 8-9자리이며(예: `AA1234567`. 2005년 이후 대문자 2자 시리즈가 일반적이고 구형은 대문자 1자), 시리즈 문자 목록은 확인 필요. 번호 자체에 체크섬은 없고 MRZ 에 7-3-1 체크 디지트가 붙는다.
  - 예시: `AA1234567`, `A1234567` (형식 예시)
- **법적 근거**:
  - 법령: 외무부 여권 발급 규정 B.E. 2548, PDPA 제6조
  - 감독기관: 외무부 영사국, PDPC
  - 노출 금지 이유: 정부 발급 신분증 번호로서 항공·비자·은행 KYC 에 쓰인다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[A-Z]{1,2}[0-9]{7}[0-9]?` | `AA1234567`, `A1234567`, `AB12345678` (`ABC1234567`, `A123456` 은 거부) | score 사용 고려. `대문자 1-2 + 숫자 7` 은 이탈리아·폴란드 여권, 인도·베트남 여권, 미국 A-Number, 제품 코드와 겹치고, 9자리 표기(`A12345678`)는 기존 `us_passport` 패턴(`[a-zA-Z]\d{8}`)과 같은 값을 잡는다(같은 점수면 등록 순서가 보고 `pii_type` 을 정한다). 선택 꼬리는 MRZ 체크 디지트 표기용이며, 체크 디지트 동반형은 9자리(`A12345678`)와 10자리(`AB12345678`) 두 가지가 생기므로 `mrz_731` 검증기는 "`대문자 1 + 숫자 8` 또는 `대문자 2 + 숫자 8` 이면 검사, 그 외 길이는 통과" 로 분기한다. `boundary_check: true` 적용 |

    오탐: 중간~높음.
  - **byte-scan handwritten**: 가능하나 이점이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: regex + `mrz_731`(숫자 8자리 동반 표기에만). 점수 체계 도입 후 낮은 `score` 검토.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 번호 자체에는 없다. MRZ 체크 디지트 동반 시 `mrz_731`(de_DE 문서).
- **채택 여부 및 근거**: 채택. 정부 발급 신분증 번호이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `หนังสือเดินทาง`, `พาสปอร์ต`, `เลขที่หนังสือเดินทาง`, `passport`

### th_driver_license

- **설명**: 운전면허번호. DLT 가 발급하는 카드형 면허증의 번호는 8자리 숫자라는 자료와, 2014년 이후 전자 면허증은 국민 ID 를 함께 인쇄한다는 자료가 있으나 공식 명세를 확인하지 못했다(확인 필요). 면허 기록은 DLT 에서 국민 ID 로 조회된다.
  - 예시: `12345678` (형식 예시. 구조 미확인이라 검증하지 않았다)
- **법적 근거**:
  - 법령: Motor Vehicle Act 제42조 이하, PDPA 제6조
  - 감독기관: DLT, PDPC
  - 노출 금지 이유: 신분증 대용으로 쓰이며 DLT 기록과 연결된다. 다만 국민 ID 가 실질 키라 면허번호 자체의 식별력은 낮다.
- **결정론적 검출 가능성**: 가능하나 형식이 확인되지 않았다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{8}` | `12345678` | **score 사용 필요**. 8자리 숫자열은 다른 모든 숫자열과 겹친다. 구조 확인 전에는 등록하지 않는다 |

  - **byte-scan handwritten**: 구조 확인 후 판단.
  - **Aho-Corasick**: 부적합.
  - **권장**: 형식 명세 확인 후 결정. 등록하더라도 낮은 `score` 가 필요하다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 확인 필요.
- **채택 여부 및 근거**: 조건부 채택. 점수 체계 도입과 형식 명세 확인이 조건이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `ใบขับขี่`, `ใบอนุญาตขับขี่`, `เลขที่ใบขับขี่`, `driver's license`, `driving licence`

### th_bank_account

- **설명**: 은행 계좌번호. 태국은 IBAN 을 쓰지 않으며 주요 은행(방콕은행, 카시콘, SCB, 크룽타이 등)은 10자리 숫자 계좌번호를 `123-4-56789-0` 처럼 `3-1-5-1` 로 표기한다(일부 은행은 12자리 등 예외 있음, 확인 필요). 체크섬은 공개되어 있지 않다. PromptPay 는 계좌 대신 국민 ID 나 휴대전화번호로 송금한다.
  - 예시: `123-4-56789-0` (형식 예시), `1234567890` (숫자만 표기)
- **법적 근거**:
  - 법령: Financial Institutions Business Act 제154조 (은행 비밀), PDPA 제6조
  - 감독기관: BOT, PDPC
  - 노출 금지 이유: 계좌번호 + 은행명으로 송금 대상 지정과 계좌 도용 시도가 가능하며, 태국은 "뮬 계좌(บัญชีม้า)" 사기가 사회 문제라 계좌 정보 유출이 민감하다.
- **결정론적 검출 가능성**: 구분자 표기는 가능, 숫자만 표기는 약하다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{3}-[0-9]-[0-9]{5}-[0-9]` | `123-4-56789-0` | score 사용 고려. `3-1-5-1` 하이픈 구조는 특이해서 오탐이 낮지만 검증기가 없다. `boundary_check: true` 적용 |
    | `[0-9]{10}` | `1234567890` | **score 사용 필요**. 10자리 숫자열은 전화번호와 겹친다. 점수 체계 도입 전에는 등록하지 않는다 |

    오탐: 구분자 표기는 낮고, 숫자만 표기는 높다.
  - **byte-scan handwritten**: 이점이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: 구분자 표기는 regex 로 바로 등록, 숫자만 표기는 점수 체계 도입 후.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 체크섬 없음(은행별 규칙 비공개).
- **채택 여부 및 근거**: 채택. 구분자 표기는 바로 등록하고, 숫자만 표기는 점수 체계 도입이 선행 조건이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `เลขบัญชี`, `เลขที่บัญชี`, `บัญชีธนาคาร`, `โอนเงิน`, `พร้อมเพย์`, `promptpay`, `account number`, `bank account`

### th_phonenumber

- **설명**: 태국 전화번호. 국가번호 `+66`, 국내 접두 `0`. 휴대전화는 `06x`·`08x`·`09x` 로 시작하는 10자리(`081-234-5678` 처럼 3-3-4 로 띄어 씀), 유선은 방콕 `02` + 7자리 또는 지방 `03x`·`04x`·`05x`·`07x` + 6자리의 9자리이다(`06x` 는 이동전화 대역이라 유선에 없다). 국제 표기에서는 선행 `0` 을 뺀다.
  - 예시: 휴대전화 `081-234-5678`, `0812345678`, `+66 81 234 5678`, `+66812345678`, `061-234-5678`, `099 123 4567`. 유선 `02-123-4567`, `021234567`, `+66 2 123 4567`, `053-123-456`, `053123456`, `+66 53 123 456`. 모두 형식 예시이다.
- **법적 근거**:
  - 법령: Telecommunications Business Act, NBTC SIM 실명 등록 규정, PDPA 제6조
  - 감독기관: NBTC, PDPC
  - 노출 금지 이유: 휴대전화번호는 PromptPay 송금 키·은행 앱 OTP·LINE 계정의 열쇠이며 SIM 이 국민 ID 에 연계되어 있다. 태국은 콜센터 사기와 SMS 피싱이 특히 많다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `(\+66[ -]?\|0)[689][0-9][ -]?[0-9]{3}[ -]?[0-9]{4}` | `081-234-5678`, `0812345678`, `+66 81 234 5678`, `+66812345678`, `061-234-5678`, `099 123 4567` (`021-234-5678`, 9자리는 거부) | score 사용 고려. `0[689]` 접두와 10자리 고정 길이가 필터이지만 구분자 없는 10자리 숫자열은 다른 번호와 겹친다. 통신사 접두 표를 넣으면 좁아진다. `boundary_check: true` 적용 |
    | `(\+66[ -]?\|0)(2[ -]?[0-9]{3}[ -]?[0-9]{4}\|[3-57][0-9][ -]?[0-9]{3}[ -]?[0-9]{3})` | `02-123-4567`, `021234567`, `+66 2 123 4567`, `053-123-456`, `053123456`, `+66 53 123 456` (`081-234-5678`, `061234567`(06 은 이동전화 대역), 8자리, `053 123 4567`(10자리)은 거부) | score 사용 고려. `02`·`0[3457]` 접두 + 9자리 고정 길이가 필터라 다른 국가의 유선번호보다 정밀하다. 배정된 2자리 지역번호 표(20여 개)를 넣으면 더 좁아진다 |

    오탐: 휴대전화·유선 모두 중간. 유선도 길이가 고정이라 "사용 필요"까지 내리지 않았다.
  - **byte-scan handwritten**: 가능하나 이점이 적다.
  - **Aho-Corasick**: `+66`(3바이트)는 anchor 로 적합하다. 국내 표기는 `08`·`09`·`06`·`02` 가 2바이트라 흔하지만 `kr_phonenumber` 의 `010` 과 비슷한 역할을 할 수 있다.
  - **권장**: 휴대전화·유선 모두 regex. 별도 recognizer 로 나누되 유선도 바로 등록한다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 통신사 접두 표와 지역번호 표(NBTC 공고, 최신 목록으로 재확인 필요).
- **채택 여부 및 근거**: 휴대전화·유선 모두 채택. 길이가 고정이라 오탐이 제어 가능하다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `เบอร์โทร`, `เบอร์โทรศัพท์`, `โทรศัพท์`, `เบอร์มือถือ`, `มือถือ`, `ติดต่อ`, `line`, `phone`, `mobile`

### th_vehicle_plate

- **설명**: 차량 번호판(ป้ายทะเบียน). 승용차는 `태국 문자 1-2자 + 숫자 1-4자리`(예: `กข 1234`)이고 2012년 이후 `숫자 1 + 태국 문자 2자 + 숫자 1-4자리`(예: `1กข 1234`) 형식이 추가되었으며, 아래 줄에 등록 도(道) 이름이 태국어로 붙는다. 픽업·오토바이는 문자 수와 배치가 다르다. 태국 문자는 자음 44자 중 일부만 쓰인다(확인 필요).
  - 예시: `กข 1234`, `1กข 1234`, `กข1234`, `ฮฮ 9999` (형식 예시)
- **법적 근거**:
  - 법령: Motor Vehicle Act 제6조 이하, DLT 번호판 규정, PDPA 제6조. DLT 등록부에서 번호판으로 소유자가 특정된다.
  - 감독기관: DLT, PDPC
  - 노출 금지 이유: DLT 조회로 소유자 정보가 특정되고, 통행·주차 기록과 결합하면 위치 추적이 가능하다. 공개 노출되는 번호라 단독 위험도는 낮다.
- **결정론적 검출 가능성**: 가능하나 정밀도가 낮다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `([1-9](ก\|ข\|ฃ\|ค\|ฅ\|ฆ\|ง\|จ\|ฉ\|ช\|ซ\|ฌ\|ญ\|ฎ\|ฏ\|ฐ\|ฑ\|ฒ\|ณ\|ด\|ต\|ถ\|ท\|ธ\|น\|บ\|ป\|ผ\|ฝ\|พ\|ฟ\|ภ\|ม\|ย\|ร\|ล\|ว\|ศ\|ษ\|ส\|ห\|ฬ\|อ\|ฮ){2}\|(ก\|ข\|ฃ\|ค\|ฅ\|ฆ\|ง\|จ\|ฉ\|ช\|ซ\|ฌ\|ญ\|ฎ\|ฏ\|ฐ\|ฑ\|ฒ\|ณ\|ด\|ต\|ถ\|ท\|ธ\|น\|บ\|ป\|ผ\|ฝ\|พ\|ฟ\|ภ\|ม\|ย\|ร\|ล\|ว\|ศ\|ษ\|ส\|ห\|ฬ\|อ\|ฮ){1,2}) ?[0-9]{1,4}` (태국 자음 44자를 리터럴 대안으로 나열. 신형 `숫자 1 + 자음 2` 와 구형 `자음 1-2` 를 분리) | `กข 1234`, `1กข 1234`, `กข1234`, `ฮฮ 9999` (`1ก 1234`, `ปี 2024`(모음 부호 뒤 숫자)는 거부) | **score 사용 필요**. 태국 자음 1-2자 + 숫자는 태국어 문장 안의 "자음으로 끝나는 단어 + 숫자" 조합(`ห้อง 101` → `อง 101`, `คน 3` 등)과 광범위하게 겹치고, `boundary_check` 가 태국 문자를 검사하지 않아 단어 꼬리 2자만 잘려 매치된다(Python 으로 확인). 태국어는 단어 사이에 공백이 없으므로 "태국 문자 인접 = 오탐" 으로 볼 수도 없다(`รถทะเบียนกข 1234ครับ` 의 `กข 1234` 는 정탐). 점수 체계 도입 전에는 등록하지 않는다 |

    오탐: 높다. 리터럴 대안 44개 × 2 자리는 DFA 상태를 늘리므로, 등록한다면 byte-scan 이 메모리 면에서도 유리하다.
  - **byte-scan handwritten**: 부분적으로 적합. UTF-8 3바이트 태국 자음을 표로 대조하고, 실제 번호판에 쓰이는 자음 집합과 도 이름(77개)이 뒤따르는지 검사하는 논리를 코드로 둘 수 있다. 앞 바이트가 태국 문자인지로 걸러내면 `ห้อง 101` 같은 단어 꼬리 매치는 줄지만, 띄어쓰기 없는 문장 안의 정탐(`รถทะเบียนกข 1234ครับ`)도 함께 잃으므로 재현율 희생을 감수하는 선택이다. regex 로는 이런 규칙을 표현할 수 없다.
  - **Aho-Corasick**: 부적합. 접두가 열려 있다.
  - **권장**: 점수 체계 도입 후 등록하되, 도 이름이 함께 적힌 경우(`กข 1234 กรุงเทพมหานคร`)만 잡는 byte-scan detector 로 시작하는 것을 권장한다. context_words 만으로 충분하면 regex 로 등록해도 된다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 체크섬 없음. 사용 자음 표와 도 이름 표(77개) 대조.
- **채택 여부 및 근거**: 조건부 채택. DLT 조회로 소유자 특정이 가능하지만, 태국 문자 경계 문제로 오탐이 높아 점수 체계 도입이 조건이다. 도 이름 동반 검사(byte-scan)는 권장 사항이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `ทะเบียนรถ`, `ป้ายทะเบียน`, `เลขทะเบียน`, `รถยนต์`, `license plate`

### th_company_id

- **설명**: 법인 등록번호(เลขทะเบียนนิติบุคคล). 상무부 사업개발국(DBD)이 부여하는 13자리 번호로 `0` 으로 시작하고(법인 표시) 마지막 자리는 국민 ID 와 같은 가중합 mod 11 체크 디지트이다. 법인의 납세자 번호이기도 하다. DBD 표기는 국민 ID 와 다른 `1-2-1-3-5-1` 묶음(`0-10-5-536-00001-1`)이다.
  - 예시: `0105536000011` (형식 예시. 국민 ID 와 같은 규칙으로 체크 디지트를 계산해 python-stdnum `th.moa` 로 확인)
- **법적 근거**:
  - 법령: Civil and Commercial Code, DBD 규정. DBD 데이터웨어하우스에서 **공개 조회**되고 송장·계약서에 기재된다.
  - 감독기관: DBD, 국세청
  - 노출 금지 이유: 없다. 법인 식별자이지 개인정보가 아니다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `0[ -]?[0-9]{2}[ -]?[0-9][ -]?[0-9]{3}[ -]?[0-9]{5}[ -]?[0-9]` | `0105536000011`, `0-10-5-536-00001-1` (python-stdnum `th.moa` 의 `format()` 출력과 같은 묶음) | 기본에 가깝다. `0` 접두 + 13자리 + 체크 디지트. 체크 디지트 규칙이 국민 ID 와 같으므로 `th_pin` 검증기를 첫 자리 `0` 허용 분기로 재사용한다. 미채택 항목 |

  - **byte-scan handwritten**: 이점이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: 미채택.
- **검증기**:
  - 현재: 없음
  - 구현 가능: `th_pin` 재사용(첫 자리 `0` 허용 분기).
- **채택 여부 및 근거**: 미채택. 공개 사업자 번호이다. 개인사업자는 법인 번호 대신 국민 ID 를 쓰므로 `th_national_id` 가 담당한다.
- **기존 구현 여부**: 신규 (미채택이므로 구현하지 않음)
- **context_words 후보** (재검토 시 참고): `เลขทะเบียนนิติบุคคล`, `เลขผู้เสียภาษี`, `tax id`, `company registration`

## 4. 검토 후 미채택한 항목

아래 항목은 법령상 PII 이거나 식별번호이지만 결정론적 검출이 불가능하거나 공개 번호라서 recognizer 로 등록하지 않는다.

| 항목 | 법적 근거 | 미채택 이유 |
|---|---|---|
| 사회보장 번호, 보편적 건강보장(UCS) 번호 | Social Security Act, National Health Security Act | 국민 ID 를 그대로 식별자로 쓰므로 `th_national_id` 가 담당한다. |
| PromptPay ID | BOT 규정 | 국민 ID 또는 휴대전화번호이므로 각각의 recognizer 가 담당한다. |
| 외국인 노동 허가증 번호, 핑크 카드 번호 | Royal Ordinance on the Management of Foreign Workers' Employment B.E. 2560 (2017), Civil Registration Act | 핑크 카드는 `0` 시작 13자리로 알려져 있으나 법인 등록번호와 형식이 같아 확장 시 충돌한다(확인 필요). 노동 허가증 번호는 형식 명세를 확인하지 못했다. |
| 세대 등록부(ทะเบียนบ้าน) 번호 (11자리) | Civil Registration Act | 세대 식별자이며 형식 명세를 확인하지 못했다. 주소와 결합해야 개인이 특정된다. |
| 우편번호 (5자리) | 해당 없음 | 5자리 숫자는 다른 숫자열과 구분되지 않는다. |
| 주소, 이름, 생년월일 | PDPA 제6조 | 국가 종속 항목이 아니며 regex 로 결정론적 검출이 불가능하다. 공통 항목 또는 NER 로 다룬다. |
| 생체정보, 건강 상태, 종교·인종, 범죄 기록 | PDPA 제26조 (민감 개인정보) | 민감 개인정보이지만 번호 형태로 나타나지 않는다. |
| 신용카드번호, 이메일, IP 주소 | PDPA, PCI DSS | 국가 종속 항목이 아니므로 이 문서 범위 밖이다. 기존 `card_number` 등이 담당한다. |

## 5. 구현 시 후속 작업 요약

이 문서에서 도출된, YAML·`validator.rs`·`handwritten/`·엔진에 반영할 작업 목록이다. 검증기는 **함수 구현 → YAML 등록** 순서를 지킨다(`validator::validate` 가 fail-open 이므로 순서가 바뀌면 검증 없이 통과한다).

|---|---|---|---|
| 선행 | recognizer 단위 `score` 필드와 context 가산 방식 도입 (en_US 문서 5절과 공통. 이미 완료되었으면 이 행 삭제) | 엔진 | 엔진 변경 |
| 1 | `th_pin` 검증기(가중합 mod 11, 첫 자리 `0`·`9` 배제)와 `th_national_id` recognizer 추가. 핑크 카드(`0` 시작) 포함 여부는 검증기 분기와 법인 번호 충돌을 함께 검토 | th_national_id | validator 신규, YAML 신규, 조사 |
| 2 | `th_passport` recognizer 추가 (`mrz_731` 검증기는 de_DE 작업과 공용). 기존 `us_passport` 와의 등록 순서 결정 | th_passport | YAML 신규 |
| 3 | `th_bank_account` recognizer 추가 (구분자 표기 패턴만). 숫자만 패턴은 **선행 작업 완료 후에만** | th_bank_account | YAML 신규 |
| 4 | `th_phonenumber` 휴대전화·`th_phonenumber_landline` 유선 recognizer 추가 (`boundary_check: true`) | th_phonenumber | YAML 신규 |
| 5 | `th_vehicle_plate` 는 **선행 작업 완료 후** 추가. 권장은 도 이름 동반 검사를 넣은 byte-scan detector, 대안은 regex + context_words | th_vehicle_plate | handwritten 신규 (또는 YAML 신규) |
| 6 | `th_driver_license` 형식 명세 확인 후 등록 여부 결정. 등록하더라도 **선행 작업 완료 후에만** | th_driver_license | 조사 |

| 선택 | `th_company_id` recognizer (`th_pin` 재사용, 사업자 번호 마스킹 요구 시) | th_company_id | YAML 신규 |
