# PII 목록: vi_VN (베트남)

이 문서는 `tinicore/src/guardrails/config/pii_filter_config.yaml` 에 베트남(vi_VN) 고유 PII recognizer 가 포함되어야 하는 근거를 기록한다. 이미 YAML 에 있는 항목도 근거를 남기기 위해 포함하며, 국가에 종속되지 않는 항목(카드번호, API 키, 비밀번호, 이메일, IP 주소 등)은 다루지 않는다. 2026-09-15 현재 YAML 에 `vn_*` recognizer 는 하나도 없으므로 이 문서의 모든 항목은 신규이다. `pii_type` 접두는 ISO 3166 국가 코드에 맞춰 `vn_` 를 쓴다(locale 은 vi_VN).

## 0. 문서 작성 기준

각 항목은 다음 네 가지 기준으로 평가한다.

1. 적용 법령 또는 감독기관 규제상 노출되면 안 되는 PII 인가?
2. 그 PII 가 무엇이며, 노출을 막아야 하는 근거는 무엇인가?
3. 결정론적 방법(regex 또는 손으로 작성한 패턴 매칭)으로 검출할 수 있는가?
4. 검증기(체크섬 등)가 있어서 매칭 정확도를 높일 수 있는가? 검증기가 없어도 보안상 중요하면 채택한다.

### 검출 방식 세 가지 (결정론적 검출 가능성 항목에서 사용하는 용어)

엔진(`recognizer.rs` 의 `PiiEngine`)은 세 가지 매칭 방식을 지원하며, 어느 방식으로 찾은 매치든 같은 후처리 파이프라인(boundary check → validator → dedup → 점수 계산·임계값)을 거친다. 따라서 검증기와 context_words 는 방식과 무관하게 동일하게 적용된다.

| 방식 | 구현 위치 | 동작 | 적합한 경우 | 비용 |
|---|---|---|---|---|
| **regex** | `PatternRecognizer`, `PatternTemplateRecognizer` | 패턴을 30개 단위 청크(`DEFAULT_CHUNK_SIZE`)로 나눠 `regex_automata::hybrid::dfa`(lazy DFA)로 컴파일하고, 청크마다 텍스트를 한 번씩 스캔 | 패턴 수가 적고 구조가 단순할 때. 기본 선택지 | 패턴 수와 복잡도에 비례해 DFA 캐시 메모리와 스캔 횟수가 늘어난다. 카드번호는 105개 패턴이 문제가 되어 handwritten 으로 옮겼다 |
| **byte-scan handwritten** | `handwritten/card_detector.rs` 방식 (`MatchEngine` 직접 구현) | 텍스트를 바이트 단위로 걸으며 숫자열·영숫자열을 뽑고, 접두 표·길이·자리 규칙을 코드로 검사 | 접두가 고정 문자열이 아니라 **표**(BIN 처럼 여러 접두 구간)이거나, 주별 형식처럼 패턴 수가 많거나, 체크섬을 매칭 단계에서 바로 적용하고 싶을 때 | 메모리 거의 없음. 타입마다 detector 코드를 작성해야 한다 |
| **Aho-Corasick handwritten** | `handwritten/aho_corasick_detector.rs` (`pattern_desc_for` 에 anchor + verifier 등록) | 고정 문자열 anchor 를 하나의 automaton 으로 찾고, anchor 뒤의 바이트를 verifier 함수가 검사 | **고정 리터럴 접두**가 있고 그 뒤에 단순한 문자 집합 run 이 이어질 때 (`AKIA`, `ghp_`, `010` 등). 여러 타입을 한 automaton 에 묶어 텍스트를 한 번만 스캔한다 | 메모리 거의 없음. anchor 가 짧으면(1-2바이트) 텍스트 곳곳에서 verifier 가 호출되어 이득이 줄고, anchor 는 대소문자를 구분한다(`ascii_case_insensitive` 미사용) |

각 항목의 "결정론적 검출 가능성"에서는 regex 를 기본으로 표로 기술하고, 그 아래에 handwritten(byte-scan, Aho-Corasick) 대안의 실현 가능성과 **오탐률이 regex 대비 어떻게 달라지는지**를 함께 적는다. 오탐률은 매칭 형식이 같으면 방식과 무관하게 같고, handwritten 이 매칭 단계에서 표 대조나 체크섬을 추가로 수행하거나 (카드번호처럼) 구분자 제약을 의도적으로 풀 때만 달라진다.

### 점수 체계와 context_words (정확도가 낮은 패턴에 반드시 적용)

**현재 코드에서 context_words 는 매치를 걸러내지 않는다.** `compute_score` (`recognizer.rs`)는 context 단어가 매치 주변 ±50자 안에 있으면 1.0, 없으면 0.5 를 돌려주고, 임계값 `SCORE_THRESHOLD` 도 0.5 이므로 context 단어가 없어도 모든 매치가 살아남는다. 점수는 겹침 해소(`detector.rs`)에서 어느 매치를 우선할지 정하는 데에만 쓰인다. 따라서 "context_words 가 있으니 오탐을 걸러준다"는 가정은 현재 성립하지 않는다.

이 문서의 regex 표에서 **"score 사용 필요"** 로 표시한 패턴은, 형식만으로는 정확도가 낮아서 context 단어 없이 매칭되면 오탐이 될 가능성이 높은 것들이다. 이런 패턴을 채택하려면 Presidio 와 같은 방식의 점수 체계가 먼저 있어야 한다.

- `RecognizerConfig` 와 `PatternMeta` 에 recognizer 단위 `score` 필드(기본값 0.5)를 추가한다.
- `compute_score` 를 "기본 점수 + context 가산" 방식으로 바꾸고 임계값 0.5 는 유지한다. 가산값은 **0.5** 를 권장한다. 그러면 기존 recognizer 의 context 매치 점수가 지금과 같은 1.0 으로 유지되어 `tinicore/tests/guardrails/filter_test.rs` 의 `score == 1.0` 단정 3건(5331, 5441, 5471행)이 그대로 통과한다. Presidio 기본값 0.35 를 쓰면 통과·탈락 결과는 같지만 점수가 0.85 로 바뀌어 이 테스트들을 갱신해야 한다.
- 기존 recognizer 는 모두 기본값 0.5 이므로 통과·탈락 결과가 바뀌지 않는다. `card_number` 와 Aho-Corasick 계열은 Luhn 과 고정 접두가 이미 강한 필터라서 `score` 를 지정할 필요가 없다. `PatternMeta` 를 통해 같은 파이프라인을 타지만 값이 기본이라 영향이 없다.
- 낮은 `score` 를 준 recognizer 에는 `context_words` 를 반드시 채워야 한다. `compute_score` 는 `context_words` 가 비어 있으면 가산 없이 기본 점수를 돌려주므로, 비워 두면 모든 매치가 탈락한다.
- 정확도가 낮은 패턴은 같은 `pii_type` 을 가진 별도 recognizer(예: `us_driver_license_numeric`)로 분리해 `score: 0.3` 처럼 낮게 준다. context 없이는 0.3 으로 탈락하고, context 가 있으면 0.8 로 통과한다. pid 가 패턴 단위이고 `PatternMeta` 가 recognizer 설정을 패턴마다 복제하므로, 패턴별 점수보다 recognizer 분리가 스키마 변경이 적다.

context_words 는 소문자 부분 문자열 검색이므로 `car`, `tin`, `ead`, `ach`, `aba` 같은 짧은 단어는 `card`, `routing`, `read` 안에서도 걸린다. 점수 체계를 도입하면 이런 단어가 가산의 근거가 되므로, 짧은 단어는 목록에서 빼거나 앞뒤에 공백을 포함한 형태로 등록해야 한다.

### 엔진 제약 (regex 작성 시 유의)

- lazy DFA 이므로 **lookahead·lookbehind·역참조를 쓸 수 없다.** 배제 규칙(예: SSN 의 `000`, `666`, `9xx` 지역번호 제외)은 regex 가 아니라 `validator.rs` 의 검증 함수로 구현하거나, handwritten detector 안에서 코드로 처리한다.
- 현재 `validator.rs` 에 존재하는 검증기는 `luhn`, `rrn`, `phonenumber` 세 가지뿐이다. `rrn` 은 자릿수만 확인하고 `phonenumber` 는 항상 `true` 를 돌려준다. 아래 "검증기" 필드에서 "현재"는 이 세 가지 기준이고, "구현 가능"은 새로 작성해야 하는 검증 논리를 뜻한다.
- **`validator::validate` 는 fail-open 이다.** 모르는 검증기 이름이 오면 `true` 를 돌려준다. 따라서 YAML 에 `ssn`, `aba_routing` 같은 이름을 먼저 적고 함수를 나중에 구현하면 경고 없이 모든 매치가 통과한다. 반드시 **검증기 구현 → YAML 등록** 순서로 작업한다.
- 단어 경계 처리는 `boundary_check` 와 `boundary_check_reject_before/after` 설정으로 한다. `config.rs` 의 `boundary_check_reject_before` 필드 주석은 패턴 안의 `(?-u:\b)` 대신 이 설정을 쓰도록 안내한다(DFA 상태 수 감소). handwritten detector 도 같은 설정을 따른다.
- `RecognizerConfig` 에 대소문자 무시 옵션이 없다. 소문자 입력까지 잡으려면 패턴 안에 `(?i)` 인라인 플래그를 넣거나 문자 클래스에 소문자를 포함해야 한다. 기존 `us_passport` 는 `[a-zA-Z]` 로 소문자를 허용하고, 이 문서의 운전면허 제안은 `[A-Z]` 만 쓴다. 구현 시 통일한다.

### regex 표의 형식

각 항목의 regex 는 다음 3열 표로 기술한다. 표에 실린 모든 regex 는 Python `re` 로 예시와의 매칭을 확인했다(`(?-u:\b)` 는 `\b` 로 치환, `boundary_check` 는 인접 문자 검사로 모사).

| regex | 매칭 예시 | 비고 (score 사용 필요 등) |
|---|---|---|

"비고" 열의 표기는 다음 뜻이다.
- **score 사용 필요**: 형식만으로는 정확도가 낮다. 점수 체계 도입 후 낮은 `score` 로 등록해서 context 단어가 있을 때만 통과시킨다. 신규 패턴은 점수 체계가 없는 동안 등록하지 않는다. 이미 YAML 에 있는 기존 recognizer(en_US 의 `us_passport` 등)는 예외로, 현재 상태(오탐 감수)로 유지하다가 점수 체계 도입 후 낮은 `score` 로 전환한다.
- **score 사용 고려**: 형식만으로는 정확도가 중간이다. 검증기가 있으면 기본 점수로 충분하고, 검증기가 없거나 검증기 없이 등록한다면 낮은 `score` 를 권장한다.
- **기본**: 형식 자체가 충분히 특이해서 기본 점수 0.5 로 등록해도 된다.


### 이 문서의 regex 검증 방법에 대한 보충

엔진은 DFA 를 `MatchKind::All` 로 빌드해 겹치는 모든 매치 끝을 보고한 뒤 boundary check 와 dedup 으로 가장 긴 것을 남긴다. 엔진이 `unicode(false)` 로 DFA 를 빌드하므로 베트남어 성조 문자는 문자 클래스에 넣을 수 없으나, 베트남의 식별번호는 모두 라틴 대문자·숫자로 표기되므로 이 문서의 regex 는 ASCII 만 쓴다. context_words 의 베트남어 단어(`căn cước` 등)는 소문자 부분 문자열 검색이라 문제가 없다. 세금 코드(MST)의 체크섬은 python-stdnum 2.2 의 `stdnum.vn.mst` 와 대조했고, 나머지 번호는 체크섬이 없거나 공개되어 있지 않아 형식 규칙만 검증했다.

## 1. 적용 법령 및 감독기관

베트남은 2023년 개인정보 보호에 관한 정부령(Decree 13/2023/NĐ-CP)으로 GDPR 형 규율을 도입했고, 2025년 6월 국회가 개인정보 보호법(Luật Bảo vệ dữ liệu cá nhân)을 통과시켜 2026년 1월 1일 시행되었다. 감독기관은 공안부(Bộ Công an)의 사이버보안·하이테크범죄예방국(A05)이다. 베트남 법제의 특징은 **12자리 시민 신분번호(số định danh cá nhân)가 신분증·세금·건강보험·은행을 관통하는 단일 식별자**로 빠르게 통합되고 있다는 점이다. 이 번호는 2016년부터 출생 등록 시 부여되어 왔고 2024년 7월 시행된 신분증법(Luật Căn cước)이 이를 이어받았으며, 2025년 7월부터 개인 세금 코드가 이 번호로 대체되었으며, 건강보험·사회보험 번호도 이 번호와 연계된다. 따라서 시민 신분번호가 최우선 채택 대상이다. Decree 13 은 개인정보를 기본 개인정보와 민감 개인정보(건강·생체·금융·위치 등)로 나누고, 민감 정보 처리에 명시적 동의와 별도 보호 조치를 요구한다.

## 3. 항목별 상세

### vn_citizen_id

- **설명**: 시민 신분번호(số định danh cá nhân), 신분증(Căn cước, 구 CCCD)에 인쇄되는 12자리 번호. 구조는 `성(省)·시 코드 3(`001` 하노이 … `096` 까마우, 외국 출생은 국가 코드) + 세기·성별 1(`0` 1900년대 남, `1` 1900년대 여, `2` 2000년대 남, `3` 2000년대 여, 이후 세기마다 2씩 증가) + 출생 연도 2 + 임의 6` 이다. 체크섬은 없다. 2016년 12자리 CCCD 로 도입되어 2024년 신분증법으로 출생 시 부여되며, 2025년 7월부터 개인 세금 코드, 건강보험·사회보험·은행 계좌의 식별자로 통합되고 있다.
  - 예시: `001099012345` (하노이, 1999년생 남성 형식 예시), `079301234567` (호찌민, 2001년생 여성 형식 예시), `096212345678` (형식 예시)
- **법적 근거**:
  - 법령: Luật Căn cước 2023 제12조 (번호 구조), 제18조, Decree 13/2023 제2조 (기본 개인정보), 개인정보 보호법 2025, Thông tư 86/2024/TT-BTC (세금 코드 통합)
  - 감독기관: 공안부 C06, A05
  - 노출 금지 이유: 출생지·세기·성별·출생 연도가 번호 안에 있고, 신분증·세금·보험·은행·통신·VNeID(디지털 신원)의 단일 키로 통합되어 유출 시 신원 도용에 직결된다. 베트남은 2023-2024년 대규모 개인정보 유출 사건이 잇따라 개인정보 보호법 제정의 직접 계기가 되었다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `0(0[1-9]\|[1-8][0-9]\|9[0-6])[0-9][0-9]{2}[0-9]{6}` | `001099012345`, `079301234567`, `096212345678` (`097…`(성 코드 97), `100…`, 11자리는 거부) | score 사용 고려. 성 코드 구간(`001`-`096`)과 12자리 고정 길이가 필터이지만 구분자 없는 12자리 숫자열은 다른 번호와 겹친다. 4번째 자리를 `[0-3]` 로 좁히면(현존 인구는 1900·2000년대생) 더 좁아진다. 체크섬은 없지만 성 코드 표(`001`-`096` 안에 미배정 코드가 30여 개)와 세기·성별 자리 검사를 `vn_citizen_id` 구조 검증기로 두면 기본 점수로 등록할 수 있다. `boundary_check: true` 적용 |

    오탐: 중간. 외국 출생자의 국가 코드(성 코드 자리에 3자리 국가 코드)는 이 패턴이 잡지 못한다.
  - **byte-scan handwritten**: 가능하나 단일 패턴이라 이점이 없다.
  - **Aho-Corasick**: 부적합. 접두 `0` 뒤 성 코드가 96종이라 anchor 로 너무 많고 짧다.
  - **권장**: regex + 구조 검증기 `vn_citizen_id`(성 코드 표, 세기·성별 자리 범위, 출생 연도가 세기 자리와 모순되지 않는지).
- **검증기**:
  - 현재: 없음
  - 구현 가능: 체크섬 없음. 성 코드 표(63개 성·시, 2025년 행정구역 통합으로 34개로 줄었으나 기존 번호의 코드는 유지. 확인 필요)와 세기·성별 자리 범위 검사만 가능하다.
- **채택 여부 및 근거**: 채택. 베트남의 단일 국가 식별번호이며 구조 검증이 가능하다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `căn cước`, `can cuoc`, `cccd`, `số định danh`, `so dinh danh`, `định danh cá nhân`, `số căn cước`, `citizen id`, `vneid`

### vn_old_id (CMND)

- **설명**: 구 신분증(Chứng minh nhân dân, CMND) 번호. 2016년 이전 발급된 9자리 숫자(일부 성은 12자리)이며, 2021년부터 CCCD 로 교체가 진행되어 2025년 1월 1일부로 효력이 만료되었다. 오래된 계약서·계좌 기록에는 남아 있다.
  - 예시: `012345678` (형식 예시)
- **법적 근거**:
  - 법령: Luật Căn cước 2023 제46조 (경과 규정), Decree 13/2023
  - 감독기관: 공안부
  - 노출 금지 이유: 만료되었으나 은행·통신 기록의 조회 키로 남아 있어 신원 도용에 쓰일 수 있다.
- **결정론적 검출 가능성**: 가능하나 정밀도가 낮다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{9}` | `012345678` | **score 사용 필요**. 9자리 숫자열은 미국 여권·SSN·라우팅번호와 동일 형식이다. 기존 `us_passport` 가 이미 모든 9자리 숫자를 잡고 있어 보류 중에도 검출 공백은 없다. 점수 체계 도입 전에는 등록하지 않는다 |

    오탐: 높다.
  - **byte-scan handwritten**: 이점이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: 점수 체계 도입 후 낮은 `score` 로 등록. 효력 만료를 고려해 등록하지 않는 선택도 가능하다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 체크섬 없음.
- **채택 여부 및 근거**: 채택하되 점수 체계 도입이 선행 조건이다. 효력이 만료된 번호라 우선순위는 가장 낮다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `cmnd`, `chứng minh nhân dân`, `chung minh nhan dan`, `chứng minh thư`, `số cmnd`

### vn_health_insurance

- **설명**: 건강보험(BHYT) 카드 번호. 베트남 사회보험이 부여하는 15자리로 `가입 대상 코드 2(대문자, `DN` 기업 근로자·`HC` 공무원·`HS` 학생·`TE` 아동 등) + 급여 수준 1(`1`-`5`) + 성 코드 2(`01`-`96`) + 개인 번호 10` 구조이다(Quyết định 1351/QĐ-BHXH, 2015. 결정 번호 확인 필요). 뒤 10자리는 사회보험(BHXH) 번호와 같다. 2021년 4월 이후 발급되는 신형 카드는 10자리 BHXH 번호를 "Mã số" 로 인쇄하고 급여 수준을 별도 칸에 표시하므로, 15자리 코드는 구형 카드와 조회 시스템에 남아 있다(확인 필요). 2025년부터 시민 신분번호로 조회할 수 있다.
  - 예시: `DN4010123456789`, `HC2790123456789` (형식 예시)
- **법적 근거**:
  - 법령: Luật Bảo hiểm y tế, Quyết định 1351/QĐ-BHXH (확인 필요), Decree 13/2023 제2조 (건강 정보는 민감 개인정보), 개인정보 보호법 2025
  - 감독기관: BHXH Việt Nam, 보건부, 공안부 A05
  - 노출 금지 이유: 진료·처방·보험 청구 기록의 연결 키이며 건강 정보는 민감 개인정보이다. 대상 코드와 급여 수준이 번호에 드러나 직업·사회적 지위를 추정하게 한다.
- **결정론적 검출 가능성**: 가능하며 형식이 엄격하다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[A-Z]{2}[1-5](0[1-9]\|[1-8][0-9]\|9[0-6])[0-9]{10}` | `DN4010123456789`, `HC2790123456789` (`DN6…`(급여 수준 6), `DN499…`(성 코드 99), 14자리는 거부) | 기본. `대문자 2 + 급여 수준 + 성 코드 구간 + 10자리` 구조가 우연히 맞기 어렵다. 국방부(`97`)·공안(`98`) 소속 카드가 있다는 자료가 있으므로 성 코드 구간을 `9[0-8]` 로 넓힐지 확인 필요. 대상 코드 표(약 40종)를 리터럴 대안으로 넣으면 더 좁아진다. `boundary_check: true` 적용 |

    오탐: 낮다.
  - **byte-scan handwritten**: 가능하나 이점이 없다.
  - **Aho-Corasick**: 대상 코드 2자(`DN`, `HC`, `HS`, `TE` …)는 2바이트라 흔하지만 뒤에 숫자 13자리가 이어지는지 verifier 가 검사하면 실용적이다. 이점은 작다.
  - **권장**: regex. 대상 코드 표는 검증기로 둔다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 체크섬 없음. 대상 코드 표와 성 코드 표 대조.
- **채택 여부 및 근거**: 채택. 민감 개인정보(건강)의 연결 키이며 형식이 엄격하다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `bảo hiểm y tế`, `bao hiem y te`, `bhyt`, `thẻ bhyt`, `mã thẻ`, `vssid`, `health insurance`

### vn_social_insurance

- **설명**: 사회보험(BHXH) 번호. 10자리 숫자이며 건강보험 카드 번호의 뒤 10자리와 같다. 사회보험 수첩(sổ BHXH)과 급여명세서에 기재된다.
  - 예시: `0123456789` (형식 예시)
- **법적 근거**:
  - 법령: Luật Bảo hiểm xã hội 2024, Decree 13/2023
  - 감독기관: BHXH Việt Nam
  - 노출 금지 이유: 고용·연금·실업급여 기록의 연결 키이다.
- **결정론적 검출 가능성**: 가능하나 정밀도가 낮다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{10}` | `0123456789` | **score 사용 필요**. 10자리 숫자열은 전화번호·세금 코드와 겹친다. 체크섬이 없다. 건강보험 카드 번호 안의 뒤 10자리는 `boundary_check` 때문에 별도로 매치되지 않는다. 점수 체계 도입 전에는 등록하지 않는다 |

    오탐: 높다.
  - **byte-scan handwritten**: 이점이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: 점수 체계 도입 후 낮은 `score` 로 등록. 건강보험 카드 번호(15자리)가 실질적으로 같은 정보를 담으므로 우선순위는 낮다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 체크섬 없음.
- **채택 여부 및 근거**: 채택하되 점수 체계 도입이 선행 조건이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `bảo hiểm xã hội`, `bao hiem xa hoi`, `bhxh`, `số sổ bhxh`, `mã số bhxh`, `social insurance`

### vn_passport

- **설명**: 베트남 여권번호. `대문자 1 + 숫자 7` 의 8자리이며 일반 여권은 `B`(구형)·`C`(2022년 이후 전자여권)로 시작한다(시리즈 문자 확인 필요). 번호 자체에 체크섬은 없고 MRZ 에 7-3-1 체크 디지트가 붙는다.
  - 예시: `B1234567`, `C9876543` (형식 예시)
- **법적 근거**:
  - 법령: Luật Xuất cảnh, nhập cảnh 2019, Decree 13/2023
  - 감독기관: 공안부 출입국관리국
  - 노출 금지 이유: 정부 발급 신분증 번호로서 항공·비자·은행 KYC 에 쓰인다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[A-Z][0-9]{7}[0-9]?` | `B1234567`, `C9876543` (`B123456`, `BC1234567` 은 거부) | score 사용 고려. `대문자 1 + 숫자 7` 은 인도 여권·미국 A-Number·제품 코드와 겹치고, 9자리 표기 `B12345678` 은 기존 `us_passport` 패턴(`[a-zA-Z]\d{8}`)과 같은 값을 잡는다(같은 점수면 등록 순서가 보고 `pii_type` 을 정한다). 시리즈 문자를 `[BCN]` 등으로 좁히면 오탐이 줄지만 목록 확인 필요. 선택 꼬리는 MRZ 체크 디지트 표기용이며 9자리 매치에만 `mrz_731` 적용. `boundary_check: true` 적용 |

    오탐: 중간~높음.
  - **byte-scan handwritten**: 가능하나 이점이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: regex + `mrz_731`(9자리 매치에만). 점수 체계 도입 후 낮은 `score` 검토.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 번호 자체에는 없다. MRZ 체크 디지트 동반 시 `mrz_731`(de_DE 문서).
- **채택 여부 및 근거**: 채택. 정부 발급 신분증 번호이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `hộ chiếu`, `ho chieu`, `số hộ chiếu`, `passport`

### vn_driver_license

- **설명**: 운전면허(giấy phép lái xe) 번호. 카드형 면허증의 번호는 12자리 숫자로 `성 코드 2 + 성별·발급 회차 1 + 발급 연도 2 + 일련 7` 구조라는 자료가 있으나 공식 명세를 확인하지 못했다(확인 필요). 2025년 3월부터 공안부가 발급하는 신형 면허는 번호가 시민 신분번호(12자리)와 같다는 자료가 있어(Thông tư 12/2025/TT-BCA, 확인 필요), 맞다면 신형은 `vn_citizen_id` 가 그대로 잡고 이 항목은 2025년 이전 발급분에만 의미가 있다.
  - 예시: `012345678901` (형식 예시. 구조 미확인이라 검증하지 않았다)
- **법적 근거**:
  - 법령: Luật Trật tự, an toàn giao thông đường bộ 2024, Decree 13/2023
  - 감독기관: 공안부 C08 (2025년 교통부에서 이관)
  - 노출 금지 이유: 신분증 대용으로 쓰이며 교통 위반 기록과 연결된다.
- **결정론적 검출 가능성**: 가능하나 형식이 확인되지 않았다.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{12}` | `012345678901` | **score 사용 필요**. 12자리 숫자열은 시민 신분번호와 같은 길이라 겹친다. 구조 확인 전에는 등록하지 않는다 |

  - **byte-scan handwritten**: 구조 확인 후 판단.
  - **Aho-Corasick**: 부적합.
  - **권장**: 형식 명세 확인 후 결정. 등록하더라도 낮은 `score` 가 필요하다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 확인 필요.
- **채택 여부 및 근거**: 조건부 채택. 형식 명세 확인이 조건이다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `giấy phép lái xe`, `giay phep lai xe`, `gplx`, `bằng lái`, `bang lai`, `driver's license`

### vn_phonenumber

- **설명**: 베트남 전화번호. 국가번호 `+84`, 국내 접두 `0`. 휴대전화는 2018년 통신사 접두 통일 이후 `03x`·`05x`·`07x`·`08x`·`09x` 로 시작하는 10자리이고(`0912 345 678` 처럼 4-3-3 으로 띄어 쓰는 관행), 유선은 `02` 로 시작하는 11자리이며, 하노이 `024`·호찌민 `028` 은 3자리 지역번호 + 8자리 가입자 번호, 그 밖의 성은 4자리 지역번호(`0203`-`0297`) + 7자리 가입자 번호이다.
  - 예시: 휴대전화 `0912 345 678`, `0812345678`, `+84 912 345 678`, `0912345678`, `091-234-5678`, `+84912345678`, `0398.765.432`. 유선 `024 3826 1234`, `+84 24 3826 1234`, `02438261234`, `0236 382 1234`. 모두 형식 예시이다.
- **법적 근거**:
  - 법령: Luật Viễn thông 2023, Nghị định 91/2020/NĐ-CP (스팸 전화·메시지 금지), Decree 13/2023
  - 감독기관: 과학기술부 (구 정보통신부), 통신 사업자
  - 노출 금지 이유: 휴대전화번호는 은행 OTP·Zalo 계정·VNeID 인증의 열쇠이며, 베트남은 전화 사기(lừa đảo qua điện thoại)가 특히 많다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `(\+84[ .-]?\|0)[35789]([0-9]{2}[ .-]?[0-9]{3}[ .-]?[0-9]{3}\|[0-9][ .-]?[0-9]{3}[ .-]?[0-9]{4})` | `0912 345 678`, `0812345678`, `+84 912 345 678`, `0912345678`, `091-234-5678`, `+84912345678`, `0398.765.432` (`0212 345 678`(유선 접두), 9자리, 11자리는 거부) | score 사용 고려. `0[35789]` 접두와 10자리 고정 길이가 필터이지만 구분자 없는 10자리 숫자열은 다른 번호와 겹친다. 통신사 접두 표(`032`-`039` Viettel, `081`-`085`·`088` Vinaphone, `090`·`093` MobiFone 등)를 넣으면 좁아지며, 미배정 대역(`030`·`031`, `050`·`051`·`053`·`054`·`057`, `071`-`075`, `095`)은 배제 목록에 둔다. 두 대안(4-3-3, 3-3-4)은 `MatchKind::All` 에서 모두 시도된다. `boundary_check: true` 적용 |
    | `(\+84[ .-]?\|0)2([0-9][ .-]?[0-9]{4}[ .-]?[0-9]{4}\|[0-9]{2}[ .-]?[0-9]{3}[ .-]?[0-9]{4})` | `024 3826 1234`, `+84 24 3826 1234`, `02438261234`, `0236 382 1234` (`0912 345 678`, 10자리는 거부) | score 사용 고려. `02` 접두 + 11자리 고정 길이가 필터라 다른 국가의 유선번호보다 정밀하다. 지역번호 표(3자리 2개 + 4자리 약 60개)를 넣으면 더 좁아진다 |

    오탐: 휴대전화·유선 모두 중간. 다른 국가와 달리 유선도 길이가 고정이라 "사용 필요"까지 내리지 않았다.
  - **byte-scan handwritten**: 가능하나 이점이 적다.
  - **Aho-Corasick**: `+84`(3바이트)는 anchor 로 적합하다. 국내 표기는 `03`·`05`·`07`·`08`·`09`·`02` 가 2바이트라 흔하지만 `kr_phonenumber` 의 `010` 과 비슷한 역할을 할 수 있다.
  - **권장**: 휴대전화·유선 모두 regex. 별도 recognizer 로 나누되 유선도 바로 등록한다.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 통신사 접두 표와 지역번호 표(과학기술부 공고, 최신 목록으로 재확인 필요).
- **채택 여부 및 근거**: 휴대전화·유선 모두 채택. 길이가 고정이라 오탐이 제어 가능하다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `điện thoại`, `dien thoai`, `số điện thoại`, `sđt`, `sdt`(3글자, 제외), `di động`, `liên hệ`, `zalo`, `phone`

### vn_vehicle_plate

- **설명**: 차량 번호판(biển số xe). `성 코드 2 + 시리즈 문자 1(+ 숫자 또는 문자 1) + 하이픈 + 일련번호 5(`123.45` 로 점을 찍어 표기)` 구조이며(`30A-123.45` 하노이 승용차, `51F1-123.45` 호찌민 오토바이, `29LD-123.45` 외국인 투자 기업 차량), 2010년 이전 구형은 일련번호가 4자리(`30A-1234`)이다. 2023년 이후 번호판이 소유자 신분번호에 귀속(biển số định danh)되어 차량이 아닌 사람에게 묶인다.
  - 예시: `30A-123.45`, `30A-12345`, `51F1-123.45`, `29LD-123.45`, `30A 123.45`, 구형 `30A-1234`, `51F-1234`. 모두 형식 예시이다.
- **법적 근거**:
  - 법령: Thông tư 24/2023/TT-BCA (신분번호 귀속 도입, 2023-08-15 시행), Thông tư 79/2024/TT-BCA (후속 규정), Luật Trật tự, an toàn giao thông 2024, Decree 13/2023
  - 감독기관: 공안부 C08
  - 노출 금지 이유: 2023년 이후 번호판이 소유자 신분번호에 직접 귀속되어 개인 식별력이 다른 국가보다 높다. 통행·주차 기록과 결합하면 위치 추적이 가능하다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{2}[ -]?[A-Z][0-9A-Z]?[ -]?[0-9]{3}\.?[0-9]{2}` | `30A-123.45`, `30A-12345`, `51F1-123.45`, `51-F1 123.45`, `29LD-123.45`, `30A 123.45` (`3A-123.45`, `30A-1234` 는 거부) | 기본. `숫자 2 + 문자 + 구분자 + 5자리` 구조가 특이하고 점 표기(`123.45`)는 더욱 특이하다. 성 코드 표(`11`-`99` 중 배정된 것)로 좁힐 수 있다. `boundary_check: true` 적용 |
    | `[0-9]{2}[ -]?[A-Z][0-9A-Z]?[ -]?[0-9]{4}` (구형) | `30A-1234`, `51F-1234` | score 사용 고려. 구형. `숫자 2 + 문자 + 숫자 4` 는 제품 코드와 겹치고 검증기가 없으므로 점수 체계 도입 후 등록한다 |

    오탐: 5자리 형식은 낮고, 4자리 구형은 중간이다.
  - **byte-scan handwritten**: 가능하나 이점이 없다.
  - **Aho-Corasick**: 부적합. 접두가 성 코드 숫자라 고정 리터럴이 없다.
  - **권장**: regex. 구형 패턴은 점수 체계 도입 후 낮은 `score` 검토.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 체크섬 없음. 성 코드 표 대조.
- **채택 여부 및 근거**: 채택. 소유자 신분번호에 귀속되어 식별력이 높고 형식이 특이하다.
- **기존 구현 여부**: 신규
- **context_words 후보**: `biển số`, `bien so`, `biển số xe`, `biển kiểm soát`, `xe máy`, `ô tô`, `license plate`

### vn_tax_code

- **설명**: 세금 코드(Mã số thuế, MST). 국세청이 부여하는 10자리 번호이며 지점은 `-` + 3자리를 붙인 13자리이다. 앞 2자리는 등록 성 코드, 10번째 자리는 앞 9자리에 가중치 `31 29 23 19 17 13 7 5 3` 을 곱한 합의 mod 11 로 계산한 체크 디지트(`10 - r`)이다. 개인 납세자에게도 같은 형식의 코드가 부여되었으나, 2025년 7월 1일부터 개인 세금 코드는 12자리 시민 신분번호로 대체되었다(Thông tư 86/2024/TT-BTC). 사업자 코드는 세무 당국·기업등록 포털에서 공개 조회된다.
  - 예시: `0100123453`, `0300123450`, `0100123453-001` (형식 예시. python-stdnum 으로 체크 디지트 확인)
- **법적 근거**:
  - 법령: Luật Quản lý thuế 2019 제30조, 제35조, Thông tư 86/2024/TT-BTC. 사업자 세금 코드는 송장·간판·웹사이트에 기재가 의무이고 공개 조회된다.
  - 감독기관: 세무국 (Cục Thuế, 구 Tổng cục Thuế)
  - 노출 금지 이유: 약하다. 사업자 코드는 공개 번호이고, 개인 코드는 시민 신분번호로 대체되어 `vn_citizen_id` 가 담당한다. 구 개인 세금 코드가 남은 문서에서만 의미가 있다.
- **결정론적 검출 가능성**: 가능.
  - **regex** (기본):

    | regex | 매칭 예시 | 비고 (score 사용 필요 등) |
    |---|---|---|
    | `[0-9]{10}(-?[0-9]{3})?` | `0100123453`, `0100123453-001`, `0100123453001` | score 사용 고려. 10자리 숫자열이지만 `vn_mst` 검증기(약 1/11)로 좁힐 수 있다. 미채택 항목 |

  - **byte-scan handwritten**: 가능하나 이점이 없다.
  - **Aho-Corasick**: 부적합.
  - **권장**: 미채택.
- **검증기**:
  - 현재: 없음
  - 구현 가능: 위 가중합 mod 11(python-stdnum `vn.mst` 와 동일. 3-9번째 자리가 모두 `0` 인 번호와 지점 `000` 은 배제).
- **채택 여부 및 근거**: 미채택 (보류). 사업자 코드는 공개 번호이고 개인 코드는 시민 신분번호로 대체되었다. 구 개인 세금 코드 보호 요구가 생기면 재검토한다.
- **기존 구현 여부**: 신규 (미채택이므로 구현하지 않음)
- **context_words 후보** (재검토 시 참고): `mã số thuế`, `ma so thue`, `mst`, `tax code`

## 5. 구현 시 후속 작업 요약

이 문서에서 도출된, YAML·`validator.rs`·`handwritten/`·엔진에 반영할 작업 목록이다. 검증기는 **함수 구현 → YAML 등록** 순서를 지킨다(`validator::validate` 가 fail-open 이므로 순서가 바뀌면 검증 없이 통과한다).
