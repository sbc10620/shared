## Overall Assessment

This is a substantial, well-documented PR adding a PII guardrails engine, host-side admission gates, and background egress masking. The documentation density is unusually high and mostly earns its keep. However, there are several real issues worth addressing.

---

## Critical / High Priority

### 1. `agent_loop` unbounded history scan — DoS / quadratic cost concern
`tinicore/src/agent/loop_.rs`: When `user_input_verified = false` (the default for **every** path that doesn't opt in), `agent_loop` scans **every** user message in `conversation_history` through the input guardrail chain on **every turn**. The PR itself documents the engine cost at **~17.5 µs/byte** on varied text (`LARGE_SCAN_WARN_BYTES` doc). For a long conversation with large messages (say 100 KB of cumulative user text), that's ~1.75s **per turn**, re-paid every turn — and the DFA scan happens inside `spawn_blocking` but the `GuardrailInput` checks are awaited sequentially per message in a `for` loop. The stated rationale (un-windowed history means a capped scan is security theater) is sound for *correctness*, but the *performance* consequence isn't addressed: a long-lived conversation gets progressively slower with no bound. Consider at minimum:
- Caching which messages already passed (by message id/hash) so re-scans are incremental rather than full.
- Documenting the expected cost profile so operators understand the trade.

The doc comment acknowledges "a credential that made it into persisted history is a data-hygiene problem" — fine — but the repeated full rescans are a fixable cost, not an inherent one.

### 2. `verify_ftp` — potential panic on short input
`tinicore/src/guardrails/handwritten/aho_corasick_detector.rs`:
```rust
let anchor_start = if anchor_end >= 7 && bytes[anchor_end - 7] == b's' {
    anchor_end - 7
} else {
    anchor_end - 6
};
```
If `anchor_end < 6`, `anchor_end - 6` underflows and panics in debug (wraps in release → out-of-bounds slice later). AhoCorasick can only match `ftp://` at `anchor_end >= 6`, so in practice this is unreachable via the automaton — but `verify_kr_phonenumber` has the same shape with `anchor_end - 3` for anchor `"010"` (always ≥ 3, safe). For `ftp://` specifically, a 6-byte anchor guarantees `anchor_end >= 6`, so it's safe today only by construction. Worth a `debug_assert!` or defensive check since these verifiers are also unit-testable in isolation.

Also in `verify_ftp`, `parse_ipv4` calls `std::str::from_utf8(...)` on digit bytes — fine — but `bytes[pos]` is indexed after a `digit_run > 3` early return, so indexing is guarded. OK.

### 3. `EgressMask::mask_llm_request` skips `ToolResultMultipart` block text under role check only
In `pii_masking.rs`, `LlmContent::Multipart | ToolResultMultipart` iterates `ContentBlock::Text` — correct — but note the `LlmContent::AssistantTurn` arm only handles `text: Some`, and `reasoning_trace`/`tool_calls` JSON are deliberately skipped (documented as matching the main turn's gap). Acceptable, but the documented "same gap the main turn already has" means tool-call arguments carrying PII leave the device unmasked on background calls. This is a known hole being shipped — it should be tracked in an issue referenced from the comment so it doesn't get lost.

## Medium Priority

### 4. `resolve_overlaps` — BTreeMap insert drops silently on duplicate `start`
`tinicore/src/guardrails/detector.rs`: two candidates with the **same `start`** but non-overlapping (e.g. `[0,5)` and `[0,5)` identical spans from different recognizers — the config explicitly produces these, see the stripe_standard/restricted NOTE) will both attempt `accepted.insert(span.start, span)`. The second insert silently **overwrites** the first (or is dropped if keys equal — actually `BTreeMap::insert` overwrites). Two identical spans from stripe_standard_api_key and stripe_restricted_api_key collapse to one. The test `dedupe_contained_matches_keeps_both_when_spans_are_identical` in `recognizer.rs` shows the engine intends to keep both, but `resolve_overlaps` (the detector layer) keeps exactly one. Given the config comment says "This is intentional — the two types are semantically distinct", the behavior divergence between layers is at least inconsistent. Since masking/blocking outcome is identical, impact is low, but the asymmetry should be documented or unified.

### 5. `suppressed-delta` delivery can duplicate text for partial streams
`tinicore/src/llm/client.rs` (`call_llm_streaming_once`): when `suppress_live_deltas` is true, deltas are withheld, then one `events.on_text_delta(&text_content)` delivers the full text at the end. But `text_content` is `accumulated_text` **after** demasking — and the suppression flag is only recomputed per call, not per attempt. On the `/responses` → `/chat/completions` fallback path (two attempts of `call_llm_streaming_once` per logical call), if attempt 1 streams some deltas before erroring mid-stream... actually deltas are either all-suppressed or all-forwarded per attempt, and a failed attempt's forwarded deltas before the error would already have reached `events`, then attempt 2 also forwards. That's a pre-existing fallback concern, but the new suppression makes the *suppressed* case cleaner while the *unsuppressed-masking-inactive* case retains the old behavior. Fine — but worth confirming the fallback path with masking active doesn't deliver "one full chunk" twice (once per attempt where both complete). Since the first attempt must fail for the second to run, and failure aborts before the final chunk is sent, this appears safe. Recommend a test pinning it.

### 6. `char_window_end` off-by-one semantics
`tinicore/src/guardrails/recognizer.rs`:
```rust
if (bytes[pos] & 0xC0) != 0x80 && pos > end {
    count += 1;
    if count == n_chars {
        return pos;
    }
}
```
For ASCII `"hello world"`, `char_window_end(s, 0, 3)` returns 3 — correct as "byte offset of the 3rd char *after* end". But the character *at* `end` is skipped (`pos > end`), meaning the window is `[start-50, end+50)` exclusive of the char at `end` itself... which is the last char *of the match*. That matches the documented "original skip_while semantics". Tests pin this. OK — no action, just noting I verified it.

### 7. `verify_kr_phonenumber` greedy 4-then-3 can miss valid 3-digit match
```rust
for mid_len in [4, 3] {
    if charset_run_len(bytes, pos, digit) < mid_len { continue; }
    ...
}
```
For `"010-12345-6789"` (5-digit middle, invalid grouping), `mid_len=4` consumes 4 digits, then separator check fails on `5`, then `mid_len=3` consumes `123`, separator `4` isn't a separator so `after_sep` stays, then needs 4 digits — `45-6` fails. Correctly no match. But for `"010 1234 5678"`: `mid_len=4` → `1234`, sep ` `, then `5678` ✓. And `"010 123 4567"`: `mid_len=4` fails (only 3 digits before space... wait, `charset_run_len` at `pos` sees `123` then space stops it → run=3 < 4, so `continue`), `mid_len=3` ✓. The greedy order is correct. However, a subtle case: `"010-12345678"` — `mid_len=4` consumes `1234`, then optional-sep sees `5` (not sep), then needs 4 digits `5678` ✓ → matches `010-12345678` as phone. Whether that's desired depends on the original regex `([0-9]{3,4})` greedy semantics — regex would also match this way. Consistent. No action.

### 8. `argo-md/agent.rs` — admission gate runs but `user_input_verified = true` set unconditionally later
The gate calls `run_input_guardrails_with_text(user_text, None)` — note `None` for `per_run`. But `config.guardrails` is **not** set here (unlike `repl.rs`/`run_tui.rs` which do `config.guardrails = pii_input_guardrails.cloned()`), and yet `config.user_input_verified = true`. This means: if a PII guardrail set exists **globally** (e.g. via `ARGO_GUARDRAIL_DENY_*` env chains installed by `install_guardrails_from_env`), the host gate checked it (via `global_guardrails()` resolution inside `run_input_guardrails_with_text`) — good. But `agent_loop` with `user_input_verified = true` will check only the latest message against `guardrail_set.input` — resolved from `config.guardrails` (None) + global. So the loop's defense-in-depth pass does run against the global set for the latest message. Consistent. But unlike tinicli, the desktop app never installs the tinicli PII set — the desktop path relies solely on env-configured global guardrails. Is `install_pii` ever called for argo-md? I don't see it in this diff — meaning `pii_mode`/masking is CLI-only. If intentional, document it; the comment in `agent.rs` says "the host-side complement to the agent_loop's own internal input guardrail pass" without noting the desktop build has no PII detector installed at all.

## Low Priority / Nits

- **`filter.rs` doc-comment mismatch**: `PiiFilter::mask`'s doc block has a stray line "Return per-chunk minimum cache capacity info for diagnostics" followed by the `min_cache_info` docs, then `mask` — the doc text for `min_cache_info` appears glued onto `mask`'s doc comment. Looks like a copy-paste artifact.

- **`compute_cache_capacity` comment** says "20% margin" while `CACHE_MARGIN_RATIO = 3.0` — the stale "20%" text appears in both `recognizer.rs` fn doc and `pii_bench.rs` header ("min × 1.2"). Update these to reflect 3.0.

- **`argo-server/runner.rs` admission returns `GatewayError::Internal`** for a user-input rejection — semantically this is a 4xx-class client error, not an internal server error. If `GatewayError` has a `BadRequest`/`InvalidInput` variant, use it; surfacing user-blocked input as "Internal" pollutes error dashboards.

- **`is_aho_corasick_type` `#[allow(dead_code)]` + `is_handwritten_type` `#[allow(dead_code)]`** — two unused helpers shipped "for future use". Prefer deleting until needed.

- **`extract_card_run` cap of 20 chars**: comment says "some maestro patterns allow 20" — but the scan loop's advance logic uses `matches.iter().rev().take_while(|&&(s, _)| s == i)` which relies on match ordering; this is fragile and non-obvious. The three-space-separated-cards test pins it — good — but a comment explaining *why* `.rev().take_while(s == i)` yields the max end would help future readers.

- **`keyword_files_available`** falls back to `std::path::Path::new(p).exists()` — a CWD-relative filesystem probe in a module whose docs insist config is "never read from disk at runtime". This is compile-time-build behavior only (`from_config`), but the inconsistency (embedded `include_str!` + disk fallback) could surprise. Since `expand_template` already gracefully skips unknown paths, consider removing the disk check entirely.

- **`tinicli/src/guardrails/pii.rs` test module placement**: the `global_install_e2e` module with its `OnceLock`-installing test lives in `--lib` alongside `build_pii_for_turn` unit tests. It's documented why (needs `pub(crate)` access), but this makes the lib test binary order-dependent: if the masking-installing test runs first, **every other test in the tinicli lib binary that exercises LLM paths** will now be masked. The doc claims no other test runs `agent_loop`/`call_llm` — that's an invariant that will silently rot. The loud `assert!(global_sensitive_masking().is_none())` guard helps, but only fails if the *other* test runs first. Acceptable given the constraints, but flag it as a maintenance hazard.
